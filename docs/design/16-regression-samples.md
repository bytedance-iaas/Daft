## 1. 目标与形态

做一个样本集，用来回归质检平台的判定效果。覆盖面尽量全；每个检测项既有该报的样本，也有不该报的对照；
每条期望值写明依据。检测项不要求对应到平台现在的某个模块。

**术语（全文统一用英文词，不再混用中译）**

| 词 | 含义 |
|---|---|
| set / subset / episode | 样本集（`anchor`、`anchor-nc`、`bases`）/ 子集（一个能直接登记到质检台的数据集）/ 条目 |
| item | 检测项，编号如 `IMG-1`；§3 的分类表共 69 项、9 个维度 |
| kind：defect / phenomenon / reference / control | item 的类型：defect 出现即是问题；phenomenon 要检出、要报告但本身不算问题；reference 只是读数或评分；control 是合法情形，不该被报 |
| level：episode / dataset | item 逐条判，还是对整个 subset 判 |
| origin：requirement / article / tools / control | item 的出处：需求方的 16 项 / Pantheon 文章 / 同类工具或标准 / 对照项 |
| expectation：present / absent / pending | 一条 episode 在一个 item 上的期望：该报 / 不该报 / 只有读数或待定 |
| basis：article / dataset_label / measured / injected / human / auto_flag / auto_label | expectation 的依据（§8.2）；后两种未经确认只进 `external` |
| verdict | 平台对一条的判决（keep / drop / held）；`expectation.json` 里我们这边的结论用 defective / clean_on_checked_items / phenomena_only / pending |
| lineage / coverage / provenance | 同一原始条目的版本共用 lineage；coverage 按 item 数 present / absent / pending / unknown；provenance 是每条的来源与 URL |


**形态：一个样本集，里面按格式分目录，每个目录下按来源分子集。非商用许可的样本另成一个样本集。**

```
tos://curation-robo-anchor/
├── anchor/v1/                      # 评测集（许可允许商用；每一条至少在一个检测项上有期望值）
│   ├── index.json                  # 总清单：每个子集的格式、来源仓库与提交号、许可、能否对外展示、条数、体积
│   ├── expectation.json            # 每条 episode 的质检期望（有什么问题 / 量过的项上没问题）；各格式目录下另有只含该格式条目的副本
│   ├── taxonomy.json               # 检测项分类表：63 项的编号、名称、类型、层级、平台现状（§3）
│   ├── lerobot_v20/<子集>/          # 每个子集是一个能直接登记到质检台的数据集
│   ├── lerobot_v21/<子集>/
│   ├── lerobot_v30/<子集>/
│   └── mcap/<子集>/
├── anchor-nc/v1/                   # 评测集，非商用许可：只在内部回归用，不对客户展示
├── bases/v1/                       # 注入基底：干净条目，不算评测集，注入故障之后才进评测集
├── truth/v1/truth.jsonl            # anchor 的期望值（逐行：一条 × 一项；expectation.json 由它生成）；legacy_droid200/ 是 v1 时期的人工判定原件
├── truth-nc/v1/truth.jsonl         # anchor-nc 的期望值
└── baseline/<平台提交号>/           # 平台在这一版上的实跑结果，回归时拿来比
```

**评测集的规则**：一条样本要进评测集，必须至少在一个检测项上有期望值（该报、不该报，或一个读数），期望值要写明依据。
指标按检测项算：某一项的检出率只用在这一项上有期望值的条目算，误报率只用「不该报」的条目算。没有期望值的条目不参与任何指标。


不做成「每种格式一个数据集」，原因是同一种格式的数据合不到一起：LeRobot 要求一个数据集里所有条目的列、维度、相机、帧率都相同，
而各来源的本体和相机各不一样（FastUMI 是 14 维末端位姿、两路 720p、20 fps；MolmoAct2 是 14 维关节、三路 360p、30 fps）。
要合并就得重采样、重编码、补列，defect 多半在字节和时序里，这样一改就没了。mcap 同理，各来源的 topic 命名不同。

子集怎么切：

- LeRobot v2.1 一条一个文件：原样取选中的条目，条目编号不变，只重写 `meta/`（条目表、统计表、总数）。
- LeRobot v3.0 多条共用文件：视频文件整个保留、一个字节不动；帧表只留选中条目的行，全局帧号从 0 重排，条目表跟着改。
  （不重排的话，平台的完整性检查会报「条目表的帧区间不连续」，实测遇到过。）
- 小数据集整个放进来，不切。

## 3. 质检维度与检测项

九个维度，71 个检测项（v0.2 的 65 项合并了两项；v0.6 按 Astra-6 的分类和 Pantheon 第二批标注补了 6 项；v1.0 按独立审计补了 FILE-10、AV-5。编号只增不改）。

- **origin** 多了一个 audit（审）：独立审计（2026-10-01）提出的项。

- **origin**（出处）：requirement（需）= 需求方的 16 项；article（文）= Pantheon 原文；tools（具）= 同类工具或标准里有的；control（—）= 对照项。表里沿用单字缩写。
- **样本现状**：「真实」是有真实样本；「合成」是只能注入；「标记」是只有自动标记，要人工复核；「缺」是还没有。
- **平台现状**：
  - 「能判」：平台有检查，会给出拒绝或待人工裁决的结论；
  - 「有读数」：结果里有相关的数，但不影响结论；
  - 「部分」：只在某些条件下能发现，条件写在后面；
  - 「没有」：没有对应的检查；
  - 「未测」：这一轮没有样本或没跑到。
- G 开头的是原文的例子（§6），数据集编号见 §5。

## 8. 期望值

### 8.1 两层文件

- **`truth.jsonl`（逐行）**：一行是一条样本在一个检测项上的期望（`present` 为 true 该报、false 不该报、null 是读数或待定），并写明依据。
  `truth/v1` 8,276 行覆盖 anchor 911 条里的每一条；`truth-nc/v1` 1,555 行覆盖 anchor-nc 160 条里的每一条。
- **`expectation.json`（逐条）**：由 `truth.jsonl` 生成（`scripts/export_expectation.py`），一条 episode 一个记录，是交付给回归用的形态：

| 字段 | 内容 |
|---|---|
| `problems` | 期望被报出来的 defect：分类表里 kind 为 defect 的 item，带范围（哪路相机、哪个通道）、帧区间、依据、读数；`level: dataset` 的是整个子集的问题，在它每一条上都重复 |
| `phenomena` | 要检出、要报告，但本身不算问题的现象：动作起止点（TASK-1）、人工接管（ACT-7）、双语标注（LABEL-4）、输入格式（SET-4） |
| `clean` | 量过或有标签、确认没问题的项（带读数） |
| `pending` | 只有读数或评分的项：深度空洞占比、0–9 评分、看不清的成败 |
| `labels` | 成败、评分等标签 |
| `external` | 别的工具对这一条的判决（Pantheon 清单的状态与标记），只用来交叉比，不算我们的期望 |
| `verdict` | 逐条级的结论：`defective`（有 episode 级的 defect）/ `clean_on_checked_items`（量过的项上没问题）/ `phenomena_only` / `pending`；数据集级的问题另列在 `dataset_level_issues` |
| `episode_id`、`lineage` | `<子集名>:<条目号>`；同一原始条目的不同版本（S4 的标反 / 修正对、以后的注入派生）共用一个 `lineage`，算指标时按它去重 |
| `attribution` | 现象从哪来：`source_capture`（采集本身）/ `source_annotation`（标注）/ `preprocessing`（转换、打包，如 RH20T 的黑帧占位列）/ `format`（格式选择，如动作列拆开） |
| `severity`、`time_s` | 有依据时才写的严重度；`time_s` 是 `[起, 止)` 秒，由帧号和 fps 换算（帧号闭区间保留），mcap 与 LeRobot 可比 |
| `source.urls`、`provenance.csv` | 每条的来源：仓库、冻结的提交号、源条目号、能直接打开的 URL（LeRobot 数据集在仓库根目录的给 hub 可视化器链接；每个文件给 `resolve/` 直链，v3.0 的共用文件附该条目的时间窗）；合成条目指向它的基底条目并标 `derived` |

**不在 `problems` 也不在 `clean` 里的项，对这一条是「未知」，不参与任何指标。** 每个样本集的 `coverage.json` 按检测项列出正例 / 反例 / 待定 / 未知的条数——
这就是每个指标的分母，也是一眼能看出「哪些项还没有样本」的地方（anchor：37 项有正例、2 项只有反例、28 项还没有任何期望；anchor-nc：8 / 5 / 56）。

| | anchor | anchor-nc |
|---|---|---|
| 条数 | 911（831 个 lineage） | 160 |
| defective | 475 | 62 |
| clean_on_checked_items | 433 | 98 |
| phenomena_only | 3（ABC-130k 的接入样本） | 0 |
| defect item（条数） | 任务失败 225、没有标注 94、夹爪通道恒定 53、机位 / 相机文件对调 46、黑帧占位流 34、记录跳变 29、相机流中途停止 14、标注错 8、过暗过曝 6、冻结 5、其余 24 项各 1–4（含注入的 22 种） | `subtask` 占位 90（数据集级）、分步不合格 32、任务失败 30、残段 1 |
| phenomenon item（条数） | 输入格式 4、合法的画面变化 1 | 动作起止点 98、双语标注 59、动作列拆开 59、人工接管 24 |

### 8.4 打分：对照表与 `score.py`

平台按「模块 + 原因码」出结果，期望按检测项写，中间隔着一张对照表。`tools/regression_samples/`（入库，CI 跑它的测试）：

- `finding_map.json`（1.3，对应注册表 1.14、分类表 1.1）：41 条规则，每条读一个模块的逐条记录（`checks/<模块>/results.jsonl`），说它报出了哪个检测项、在哪路相机。
  新合入的 `camera_defects`（随任务成败的 VLM 逐机位复核一起报花屏、抖动、镜头污染）对应 IMG-5、IMG-6、IMG-7：minor、severe 算报出，模型没回答（unknown）算没评估。
  判定线尽量用平台自己的：视觉冻结 95%、报告里「低于 0.6」的相机读数、漏斗的软分线 0.5。对照表里的问题码、细节字段、模块 id 都有
  一致性测试，平台改名时测试会失败，不会悄悄把某一项的指标变成 0。
- `score.py`：TP = 期望 present 且报了，FN = present 没报，FP = 期望 absent 却报了，TN = absent 没报；没有期望的不算。
  相机限定的期望只和同一路相机的结果比。能报这一项的模块在这条上都没跑（漏斗短路、没选、预检不支持）记 not_assessed，
  都执行出错记 error，两者都不进指标、单独列出。没有规则的项列为平台 gap；control 项看误报；SET-4 看预检能不能读。
  `--by-lineage` 按来源去重；`--baseline --max-drop --min-support` 给 CI 用：任何一项掉超过阈值就以退出码 3 结束。
- 打分 1.1（v1.0，按审计意见）：
  - **范围**：`streams=a,b` 这种两路相机的范围不再被当成整条。
  - **整条级误报**：一条只在已检查项上干净的 episode 被拒，只有拒它的模块能报这些已检查项之一时才算 FP，否则记 `dropped_outside_checked`、不进指标。
  - **数据集级**：分类表里 level 为 dataset 的项和标了 `unit: subset` 的条目，按子集只计一次。
  - **对照项**：本身带 episode 级缺陷的对照条目被拒不算对照失败；对照项守的项就是分类表的 `guards`。
  - **端到端**：`recall_end_to_end` 把没评估、执行出错、没有规则的都留在分母里，`assessed_share` 是评估到的比例；`recall` 仍是评估到的那部分。
  - **血缘加权**：一条只按同一来源里带着同一项、同一边的条目数分摊。
  - 区间定位不打分：平台多数模块不输出时间区间，回归门禁按条判（§17）。

平台 `1b30fb224` 上不用模型的 6 个模块的打分（`tos://curation-robo-anchor/baseline/1b30fb224/score/`；v1.0 用期望 1.1、打分 1.1 重打，

## 12. Pantheon 清单怎么用

每个分片是一个 JSON 数组，1,000 条 episode。关联键是 `(dataset, dataset_revision, episode_id)`，`source_locator` 给出源数据里的路径。
每条有 `quality_status`、`flags`、相机与动作的逐帧有效掩码，以及形如 `video_frozen_run_corrected_left_wrist_temporal_evidence` 的逐帧证据。
在 A1 上核过四条：它的总帧数比源数据少 1 到 2 帧，帧号可以当源数据的帧号用。

| 清单里的标记 | 判定条件（摘要） | 对应的检测项 |
|---|---|---|
| `episode_too_short` | 时长小于 5 s（平台是 1 s） | STRM-5 |
| `state_timestamp_gap`、`native_camera_timestamp_gap` | 某个间隔大于 max(1.5 倍中位数, 中位数 + 5 倍 MAD) | STRM-3 |
| `*_non_monotonic_or_duplicate` | 相邻间隔小于等于 0 | STRM-4 |
| `video_extreme_exposure`、`video_low_contrast` | 超过 25% 的帧平均亮度小于 5 或大于 250；亮度标准差小于 3 | IMG-2、IMG-3 |
| `video_duplicate_frames`、`video_frozen_run` | 相邻帧亮度差小于 0.25 的比例超过 20%；连续超过 1 s | IMG-1 |
| `visual_change_unexplained_by_action` | 画面亮度差不小于 8 而各臂几乎没动（原文说误报率高） | AV-4 |
| `*_pixel_action_corr_mismatch`、`largest_action_not_in_video` | 动作强度与画面变化的相关系数过低；最大的一步动作在所有相机里都看不到 | AV-3 |
| `action_smoothness_discontinuity`、`jump_return_event`、`gross_umi_speed` | 高–停–高；跳出去又跳回来；超过 2 m/s 或 8 rad/s | ACT-1、ACT-2 |
| `over_95_percent_static` | 超过 95% 的步没有动作 | TASK-1 |
| `*_gripper_never_acts`、`*_gripper_sensor_bug`、`normalized_gripper_out_of_range` | 夹爪从不动；相邻两步反向；开度越界 | ACT-3、ACT-5 |

### 12.2 第二批标注（`labels-2026-09-28`）怎么用

发布包每条 episode 一个 JSON：`completion`（success / failure / success_then_undone / unclear，达成与撤销的秒数）、`goal_alignment`（指令与实际任务
的关系）、`data_issues`（类别、严重度、时刻、证据文字）、`operator_mistakes`、`event_labels` 与 `tasks`（逐秒的动作事件与分步）、`idle`、
`dataset_checks`（确定性检查：`stream_pairing.crossed`、`recorded_jumps`、`gripper_channels`、`timebase.sped_up_recording`）。另有 `compare/` 下
三个别的模型在子集上的标注，可以看一致性。

| 第二批的字段 / 类别 | 我们的检测项 | 能不能由我们复算 |
|---|---|---|
| `stream_pairing.crossed` | MV-2 | 能：各相机的画面变化量与两臂各自速度的相关（第二批 a 之后加规则） |
| `recorded_jumps` | ACT-2 | 能：已有 ACT-2 规则 |
| `gripper_channels`（恒定） | ACT-3 | 能：已有 ACT-3 规则 |
| `timebase.sped_up_recording`（跳帧比例） | STRM-9 | 能：视频帧数 / 时长与状态时间轴比 |
| `completion.task_completed`、`undone_at_s` | TASK-5、TASK-10 | 不能（要模型或人）；平台跑任务成败时拿来比 |
| `data_issues.instruction_mismatch`、`goal_alignment` | LABEL-5 | 不能；抽样人工核 |
| `human_intervention` / `scene_reset` / `setup_change` / `out_of_view` | TASK-11 / IMG-12 / IMG-8 | 不能；按证据时刻抽帧人工核（复核页的做法） |
| `operator_mistakes`、`idle`、`tasks` | TASK-12、TASK-8、TASK-1 | 只能当参考读数 |

用法：确定性检查复算一致的直接写 measured；其余写 `auto_label` 进 `external`，抽样人工核过的转成 `human`。gate 用例（26 条，发布方逐帧核过）
按 `article` 同级处理，仍逐条在源数据上复核。`scripts/pantheon2_candidates.py` 把 3,546 条映射成候选（`work/pantheon2/candidates.jsonl`）。

## 16. 与 Astra-6 交付规格（`delivery-spec-v1`，2026-09-29）的比对

Astra-6 那份是「交付合同」：目录形态、三份 JSON Schema、51 项分类、校验器和 35 条待复核的种子，没有下载数据、已发布 0 条。
本篇是「已经建成的样本集」。两边互补，逐项比对如下。

**借鉴并已落实（v0.6）**

| Astra-6 的做法 | 我们的对应 |
|---|---|
| 包级 `manifest.json`：逐资产哈希、`intentionally_missing` 显式声明 | 每个子集一份 `manifest.json`（§8.3）；故意缺失 / 损坏的注入样本以后按它声明 |
| `validate_delivery.py`：跨文件一致性校验，示例与正式分开 | `validate_set.py`（§8.3）；`expectation.json` 里 `basis` 与 `confirmed` 区分依据强弱，没有「示例混进正式」的问题 |
| 全局 `episode_id = source:source_episode_id`、`lineage_group` 防同源泄漏 | `episode_id`、`lineage`（§8.1）；S4 的成对子集共用 lineage |
| `coverage.json`：按类别统计正常 / 异常，未覆盖明确写 0 | `coverage.json`（§8.1） |
| `issue_attribution`：采集 / 标注 / 预处理 / 适配器 | `attribution`（§8.1） |
| 时间范围 `[start_s, end_s)`、边界容差 | `time_s`、`boundary_tolerance_s`（§8.1）；帧号闭区间保留 |
| 分类规则：编号永不复用、最具体优先、「问题 ≠ 拒收」 | 写进 `taxonomy.json` 的 `rules`；kind「defect / phenomenon / reference / control」正是「问题与是否接受分开」 |
| 分类里我们没有的：T06 时间比例、V07 相机移位、P06 达成后撤销、P07 外部干预、P04 执行错误、D02 同源泄漏 | 加为 STRM-9、IMG-12、TASK-10、TASK-11、TASK-12、SET-6；`aliases` 记录对应关系 |
| Pantheon 第二篇的标注发布包与 gate 用例 | 第二批 a 的选材依据（§12.2） |

**不采纳，以及为什么**

| Astra-6 的做法 | 不采纳的原因 |
|---|---|
| 正式文件里每条 episode 对 profile 内的全部类别给 pass / fail / not_applicable，不允许 unknown | 69 项里多数没有可靠的自动判据，逐条全填只能靠人或假装。我们显式保留「未知」，指标只用有依据的条目，`coverage.json` 把未知量公开 |
| `expected_status` 二分：no_issue / has_issues | 把动作起止点、人工接管、双语标注这类「要检出但不是问题」的 phenomenon 和 defect 混在一起；我们分 `problems` / `phenomena` |
| Share-Alike 归入 restricted 分区 | CC BY-SA 允许商用，只是派生要同许可；GenRobot 留在 `anchor`，§9 已写清派生条件。其余许可分档一致（NC 单独成集） |
| 扩到 nuScenes、EuRoC、DNS 音频、OpenPack、HOT3D、VRS、rosbag 等通用多模态来源 | 平台只读 LeRobot / mcap / Lance 的机器人操作数据；这些格式与场景不在质检平台的输入范围内，不进回归集。缺口在 `coverage.json` 里显式记 0 |
| 音频质量（V08）、实体轨迹身份切换（E03） | 平台没有音频输入，也不做多目标跟踪 |
| 每个包配 `profile.json`、`dataset_expectation.json`、`evidence/`、`LICENSES/` 四件套 | 现阶段用 `index.json` 的许可字段、`taxonomy.json` 的 `level: dataset`、`truth.jsonl` 的 `readings` / `confirmed` 承担；证据目录等人工复核结果落定后再建 |

**Astra-6 的种子清单**：35 条全部未下载、未复核、`release_eligible=false`；其中 Pantheon 第一批例子与本篇 §6 重合（G01、G02 等），第二批的 gate 用例已并入第二批 a 的选材。

### 17.3 坚持现状

- **对照项留在分类表里**：它们本来就单列为 control 类，打分也单独算通过率；只补上它们守的项（`guards`），不迁移成样本角色。
- **不加 SET-7（跨划分的同源泄漏）**：平台没有训练 / 验证 / 测试划分的概念，样本集也不拿来训练。同源分组靠 `lineage` 与 SET-6。
- **区间级打分不做**：平台多数模块不输出时间区间；回归门禁按条判。区间写在期望里，等平台有区间输出再加定位指标。
- **不给每条判断配判定契约和用途策略**：采纳结构化范围、`check`、根血缘、事件分组；判据写在检测项定义和 `basis_legend` 里。
- **ACT-3、STRM-2 不一律降成待定**：看帧证实的保留并加 `frames_viewed`，只有看不到的（相机整条坏了）和只靠相关性的 MV-2 改待定。
- **TASK-5 仍是 defect**：平台的任务成败模块会拒掉失败条目，present 的含义不变；失败示范能不能用是交付策略的事。
