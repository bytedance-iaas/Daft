# 23 · EEF 与任务成败的 CPU 半段挪进 CPU 块；源数据按块读、只下载一次；完整性缺省只做 L1

> 状态：**设计稿 v1（2026-10-09，需求方已答复 v0 的四个问题，待与 D57 作者评审）**；需求方要求先做 S1，S1 已落地（2026-10-09）。
> 来源：需求方 2026-10-09 看时间线提出——EEF 先要算轨迹（相机运动、投影、画标记），任务成败要先截取、转码多路视频，这些 CPU 计算都算在 VLM 档里；

## 0. 摘要

### 0.1 一句话

模型模块拆成两半：CPU 半段（读数据、算轨迹与相机运动、画标记、准备送模型的视频）进 CPU 块的 `vlm_prep` 段，模型半段留在 VLM 块只发请求；
两块照旧互不过滤，每条 episode 都送模型；同一任务里一条 episode 的源数据只从 TOS 下载一次，各段共用。

### 0.3 现状（实测，2026-10-09）

| | Trossen ep0（TOS，lite 模型） | cups ep0（TOS，两路相机，lite 模型） |
|---|---|---|
| EEF 一条的总耗时 | 33.1 s | 297.4 s |
| 其中：模型意见（画标记、编码、等模型） | 7.2 s | 128.3 s |
| 其中：相机运动检查（纯 CPU） | 2.5 s | 23.7 s |

| 完整性段（CPU 块第一段；今天缺省做 L2 整读，每个字节读一遍，设计 14 §3.3） | 0–16.3 s | — |

- **EEF 的 CPU 计算记在 VLM 档**：注册表里 EEF `block="vlm", stage="vlm"`；`EefJudge.judge` 里先读轨迹、算相机运动、逐帧投影、画标记、编码，
  再等模型。它从 CPU 池拿名额（设计 17 §3.1），但 VLM 档的并发宽度是按模型接口配的，CPU 计算占着这些位置，模型接口反而闲着。
- **任务成败的视频准备也在 VLM 档**：`video_task` 调 `prepare_videos`，对每路相机用 ffmpeg 远程打开、截取、缩放、转码，再内联进请求。
- **EEF 读的比需要的多**：任务成败用预签名地址远程打开、跳到这条的时间窗再解码，只读这条那一段；EEF 却把每路视频整个文件拷进临时目录
  （`cli/eef_check.py` 的 `_fetch_key`），LeRobot v3 一个文件装多条，等于为一条下载了整批。两者在同一个 `vlm` 段、同一个 worker 里，读的是同一份视频，却各读各的。
- **同一份视频被读好几遍**（LeRobot on TOS）：完整性 L2 读全部字节、帧档经 dsfs 远程读、任务成败的 ffmpeg 远程读、EEF 拷进 `eef-media-*` 临时目录再读；
  mcap 每段各自按范围读；lance 每个命令一份 `SourceCache`，命令结束就删。

## 1. 新的块与段

```
  选中的全部 episode
      │
      CPU 块（CPU 池）；所有段经同一个块缓存读源数据（§3）
          ├──────────────────────────────┐
          ▼                              ▼
      integrity   数据完整性（缺省 L1）      vlm_prep   EEF 的 CPU 半段 · 任务成败的 CPU 半段
          │ 传全部条目（不过滤）              │
      numeric   时间戳 · 运动学 · 运动质量    │
          │                              │ 传全部条目（不过滤）
      frame     视觉质量 · 视频-动作同步      ▼
          │                         ── VLM 块（只受模型并发上限约束，04 §2.2）──
      dedup     精确去重                 vlm   EEF 模型半段 · 任务成败（+画面缺陷）
          │                              │     只发请求、收答案、出发现
          └──────────────┬───────────────┘
                         ▼
             aggregate（策略判决）→ report → verify
```

- **`vlm_prep` 是 CPU 块的第二个根、与 `integrity` 并排**：它不需要完整性、数值档、帧档的任何结论（不过滤），源数据经块缓存按需读（§3），
  所以开工就能开始，和今天 VLM 块第 0 秒就开始一样早。完整性判坏的条目照样进 `vlm_prep`；读不了数据的，`vlm_prep` 记 `error`（D33），
  模型半段没有输入、记 `error`，不发请求（同设计 17 §3.1「坏文件上的模型调用」）。
- **CPU 块从一条链变成两条**：`integrity → numeric → frame → dedup` 与 `vlm_prep`，同一个 CPU 池。块与块之间第一次有了交接（`vlm_prep` → `vlm`），但只是「交出全部条目」，
  不按结论筛。
- **VLM 档只剩等模型**：`vlm` 的 worker 不做解码、编码，时间线上 VLM 条的长度就是模型的时间。
- 没勾模型模块的任务：没有 `vlm_prep`、`vlm`，和今天一样。只勾了模型模块的任务：CPU 块只有 `vlm_prep`（加上勾了的完整性等段）。

## 2. 拆两半

### 2.1 EEF

| 半段 | 做什么（今天的代码） | 产出 |
|---|---|---|
| CPU 半段（`vlm_prep`） | 读轨迹 `load_bundle`；UMI 补缺测 `umi.fill_gaps`；有夹爪参考时的 CPU 测量 `runner.run_episode`；相机运动 `_ego_motion`；与数据集记录比对 `_attach_record`；意见模式下逐帧投影、画标记、编码 MARKED 视频（`opinion._render` + `encode_rendered_video`）；判决模式下复核窗口的图 | 部分记录：不靠模型的发现（`ego_motion_suspect`、`record_mismatch`）与读数；请求包（§2.3）|
| 模型半段（`vlm`） | 发请求、修复轮、解析答案；判决模式的 `decide.py` | `opinion_mismatch`、`inconsistent`、`unsettled` 等 |

- EEF 仍是**一个模块**、一条最终记录（C2 不拆模块）。CPU 半段写一条 `phase: prep` 的部分记录；模型半段读它、补上模型的部分，写成最终记录。
  模型半段出错时，CPU 半段的发现（如 `ego_motion_suspect`）照样保留在最终记录里——它们不靠模型，没有理由丢。
- **部分记录不是结果**：`phase: prep` 的记录只写在 `checks/<模块>/prep/` 下，`aggregate`、即时结果（`results/live.py`）、`check --resume` 的
  「已有非出错结果就跳过」都只认最终记录；所以一条只做完 CPU 半段的 episode 在判决里仍是「没有记录」，按 §4.3 第 3 步 held，和今天模型没跑完一样。

### 2.2 任务成败判定（含画面缺陷）

| 半段 | 做什么 | 产出 |
|---|---|---|
| CPU 半段（`vlm_prep`） | 取任务文本、判断有没有标注（D72、D73）；每路相机按时间窗截取、缩放、转码成送模型的片段（`prepare_videos`）；拼提示词 | 请求包；`task_text_missing` 这类不靠模型的发现 |
| 模型半段（`vlm`） | 一次请求（`video-task/2`）拿整条与每路相机的结论、画面缺陷 | `failure`、`uncertain`、`recovery`、画面缺陷各码 |

### 2.3 请求包的暂存（D77）

- CPU 半段把请求包写进 `runs/<id>/scratch/vlm/<episode>/<module>/`：`request.json`（提示词、参数、缓存键）加若干 `.mp4`。
- 模型半段读包、发请求；**答案落盘成记录之后立刻删除这个目录**。
- 在途上限：`vlm_prep` 交出、`vlm` 还没做完的条数不超过 `vlm` 并发的 2 倍（计划里写明，`held_by_downstream` 卡住 `vlm_prep`）。
  磁盘占用 = 在途条数 × 每条包大小。以 cups 为例，两路 MARKED 实测 2.8 MB、3.2 MB；任务成败一次请求的视频不超过 32 MB（`prepare_videos` 的 `max_bytes`），所以每条包不超过约 40 MB，64 条在途最坏约 2.5 GB。
- **模型半段出错时保留**：请求包等重试用，重试成功才删；暂停、停止时也保留，续跑直接用、不重新编码。任务结束（成功、失败、删除）时整个 `scratch/vlm/` 清掉，
  之后的重试、继续运行先重做 `vlm_prep`（用到的块重新下载，§3）。
- **执行裁决的子任务**（改了任务描述，设计 17 §3.4 的 `check task_success`）：提示词变了、旧包不能用，链改成 `vlm_prep(task_success) → vlm(task_success)`。
- 模型请求的缓存键照旧由提示词、视频元数据、模型算，与在哪一段编码无关；续跑时已有答案的请求不重发。

## 3. 源数据按块读、只下载一次（D78、D79）

### 3.1 完整性缺省只做 L1（D79）

| | 读多少 | 查得出 | 缺省 |
|---|---|---|---|
| L1 结构 | 每个文件读头尾几次小范围 | 文件空、parquet 头尾与尾部元数据、mp4 的 moov 与样本表（帧越过文件末尾 = 截断、帧数与 episode 长度不符）、mcap 开头标识与摘要区 CRC、索引越界 | **开** |
| L2 整读 | 每个字节读一遍 | mp4 中段整块零填充、mcap 数据块与数据区 CRC、parquet 数据页整读 | **关**（任务参数 `full_read`，原来缺省开） |
| L3 逐帧解码 | 每路视频完整解码一遍 | 结构完好但画面数据损坏 | 关（不变） |

- 关掉 L2 漏掉的：文件**中段**的零填充、mcap 数据块的 CRC 不符、parquet 数据页损坏。其中 parquet 数据页损坏照样会在数值档读行时失败，记 `error`、held，
  只是不再判废、不写明原因；mp4 中段零填充多半会让帧档或模型的解码报错（同样 held），解码器掩盖掉的那部分查不出来。
- **v1 的逐条结构校验（D51：action 非空、无 NaN/Inf、时间戳递增、各列帧数对齐）** 在设计 14 里归在 L2。它读的是 parquet，字节占比很小，
  而且关掉会让「数据行坏」从判废变成 held。本篇提议把它从 L2 挪到 L1、缺省照做（§9 问题 4）。
- 改动：注册表里数据完整性的参数 schema 加 `full_read`（布尔，缺省 false，说明写明漏掉什么）；设计 14 §3、§5.3 与 D50 的「整读」同步改；
  预检与报告里写明本任务做的是哪几层。

### 3.2 任务级块缓存（D78）

- **按需、按块**：所有读源数据的地方（帧档解码、EEF 的 `iter_clip`、任务成败的 `prepare_videos`、完整性 L1 / L2、数值档读 parquet、`vlm_prep`）
  都通过同一个读取器打开远程对象。它对 PyAV / pyarrow 表现为一个可 seek 的文件对象，读到哪个块才向 TOS 发一个范围请求（块缺省 1 MiB）。
  所以每个段只取自己用到的字节：任务成败、EEF 只取这条 episode 时间窗的那一段（加 mp4 的 moov 与前面最近的关键帧）；帧档只取抽到的帧附近；
  L1 只取头尾。
- **同一块只下载一次**：块存在 `runs/<id>/cache/blocks/`，键是「对象键 + ETag + 块号」；先读的下载，后读的（包括另一个段、另一个 worker 进程）
  直接读本地。EEF 与任务成败读的是同一份视频，第二个读的几乎不再发请求。正在下载的块用文件锁，免得两个进程同时下同一块。
- **谁删**：每条 episode 记下它碰过的块；这条在所有段都做完（CPU 块两支都交出、`vlm` 用的是请求包、不再读源数据），它独占的块就删。
  LeRobot v3 一个文件装多条，块可能被相邻两条共用，按「碰过它的 episode 都做完」才删。
- **上限**：缓存总量有上限（`CURATOR_BLOCK_CACHE_MAX_GB`，缺省按数据盘的一定比例，S0 量完定）；满了先淘汰最久没用、且所属 episode 已做完的块，
  还不够就让下载的段等一等（对最前面的段不派新条目），等后面的段放掉——这是 04 §2.3 的内存准入在磁盘上的对应。
  所以 100 GB 的数据集不会先占 100 GB：盘上只有正在处理的那些条目读过的块，最多到上限。
- **一致性**：键里带 ETag，源对象在任务期间被改就是另一份；源守卫照旧在开跑时与 `verify` 时对账。

### 3.3 各读法的改动

| 今天 | 改成 |
|---|---|
| LeRobot：dsfs / 预签名地址远程读（完整性、帧档、任务成败），EEF 整份拷进自己的 `eef-media-*` | 都经块缓存的读取器；EEF 的整份拷贝与临时目录去掉；EEF 比对数据集记录时也只读 parquet 里这条用到的行组 |
| mcap：每段按范围读（`TosObjects`，D44 改成流式） | `TosObjects` 的范围读改走块缓存，同一块不读第二遍 |
| lance：每个命令一份 `SourceCache` | 经块缓存按需读；做不到按块的读法（整份读的分片）仍按对象整份进缓存，任务级共用 |
| 本地挂载路径 | 不经缓存，直接读（和今天一样） |

可视化（设计 18）不走这个缓存，它有自己的读法与缓存。

**先在 `vlm` 段里做**（S1）：EEF 与任务成败在同一个 worker 里，先让两者共用一份块缓存（worker 级），不动别的段，就能拿到「只读需要的部分」与
「两者只下一次」；再推广到任务级、各段共用（S2）。

## 4. 注册表、planner、派发要改的

### 4.1 注册表（C1）

- 模块多一个字段 `prep_stage`：EEF、任务成败填 `vlm_prep`，其余为空。模块的 `block`、`stage` 不变（仍是 `vlm` / `vlm`），
  表示「最终记录在哪一段出」；`prep_stage` 表示「CPU 半段在哪一段」。画面缺陷 `rides_on` 任务成败，跟着它。
- 段的清单加 `vlm_prep`（CPU 块的第二个根，不 `after` 任何段）。数据完整性的参数加 `full_read`（§3.1）。
- 细码目录不变。改 C1 升版本号，`CONTRACTS.lock` 重新锁。

### 4.2 planner

- 计划（`plan.schema.json`）：一个块可以有多个根；`after` 允许跨块，`vlm` 段 `after: "vlm_prep"`。planner 校验：图无环；跨块的边只允许 `vlm_prep → vlm`。
- 并发：`vlm_prep` 按 CPU 池分（编码是 CPU 密集的），不占模型并发；`vlm` 只按模型并发上限，不再从 CPU 池拿名额。
  `vlm_prep` 与 `frame` 同时解码同一条的视频，两者都在 CPU 池与帧档的内存准入（04 §2.3）之内，不另开口子。`vlm_prep` 到 `vlm` 的在途上限写进计划（§2.3）。
- 估算：EEF、任务成败的耗时拆成「准备」（CPU）与「等模型」两部分分别估。

### 4.3 Daemon 派发

- `blocks.py`：从「两条链两个线程」改成**一张图**——每一层的输入来自它的 `after`，根层开工时拿全部条目；`vlm_prep` 每交出一条进 `vlm` 的 ready。
  仍然不看结论：有记录（成功或出错）就交接。
- `episode_state`：位置从「在哪一段」改成「每个分支到了哪一段」；续跑时 `vlm_prep` 已做完、`vlm` 未做的直接从 `vlm` 接着做（请求包还在暂存区）。
- 块缓存（§3.2）的释放与上限由派发管：一条 episode 在所有段都交出后通知缓存放掉它的块；缓存满时根层不派新条目。
- 一个块失败仍停另一个块（共享 abort），暂停、停止照旧到达所有进程。
- 时间线：按实际的段画（完整性、数值、帧、去重、`vlm_prep`；VLM 块的 `vlm`），标题不再叫「三层」。

## 7. 测试与验收

- **编排**（`tests/orchestr`，假模型端点）：每条 episode 都进 `vlm`（不过滤，完整性判坏的也进）；`vlm_prep` 出错时模型半段记 `error`、不发请求；
  暂停在 `vlm_prep` 与 `vlm` 之间、续跑后请求包被复用、不重新编码；任务结束后 `scratch/vlm/` 与 `cache/source/` 都清空。
- **结果不变**：同一数据集、同一假模型，拆段前后每条记录的发现与判决逐条一致（对账黄金基线回放不变）。
- **下载复用**：用 `tests/viz` 那套最小本地 S3 计范围请求——同一块只被 GET 一次；EEF 与任务成败一起跑时，第二个读的不再发请求；
  LeRobot v3 多条一个文件时，一条 episode 读的字节数接近它那一段的大小，而不是整个文件。
- **完整性 L1**：设计 14 的故障样本里，截断、空文件、结构坏、行坏在 `full_read: false` 下照样判废；中段零填充、CRC 不符只在 `full_read: true` 下判出。
- **实测**：DROID / Trossen / cups 各跑一遍，记 VLM 档时长、模型并发利用率、TOS 下载字节数，与 §0.3 对比，写进 §10。
