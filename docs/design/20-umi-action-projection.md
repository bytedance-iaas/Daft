# UMI 动作投影

在 EEF extension 中复用投影、连续视频、模型意见与报告链路。UMI 是手持采集轨迹，没有独立的执行器指令；结论表示记录与画面的一致性、动作的可解释性，不证明机器人可执行性。

## 输入与坐标

离线 `export-umi` 将原始 UMI 的 `dataset_plan.pkl`、每路 `camera_trajectory.csv`、原始 MP4 和显式标定转换为 LeRobot 数据集与 `trajectory.json`。pickle 只允许 NumPy 数组重建，不执行任意全局对象。导出的 action/state 均表示当前采样的绝对记录，旋转转成已有 UMI 档案的 rot6d；不是独立控制命令。

标定 JSON 必须声明 `umi-calibration/1`、数据集 id、任务文本、`T_world_slam`，以及每个 `cameraN` 的 `K`、鱼眼系数、标定图尺寸、`T_camera_tcp` 和来源。相机序号直接取 dataset plan，不按文件名或左右位置猜测。相机世界位姿来自 CSV，EEF 世界位姿来自 plan。视频按 plan 的原始帧区间选帧，CSV 按视频时间配对；丢失 SLAM 或无法配对时拒绝转换，不补单位矩阵。

`adapters/umi.py` 的独立函数 `slam_to_tag(T_slam_object, T_tag_slam=...)` 负责位姿换参考系：
`T_tag_object = T_tag_slam @ T_slam_object`，支持单个位姿或整段位姿序列。`T_tag_slam` 的方向是 SLAM → tag，
在本测试集配置中为 `T_world_slam = inverse(tx_slam_tag)`。导出器只转换 CSV 相机位姿；plan 的 TCP 已在 tag 系，不重复转换。

EEF 1.0 增补可选字段：sample 的 `umi` 声明相机所属手、历史窗口和来源；frame 的 `hands` 保存同一参考系下各手的绝对位姿和开口宽度。旧输入行为不变。每个手的轨迹允许空值表示缺测，禁止跨缺测或时间间隙连线。该入口走建议性模型意见。

REST 接口与模块参数不增加 UMI flag：仍通过现有上传接口提交 `trajectory.json`，任务选择
`eef_video_consistency` 并传 `trajectory_json: upload:<handle>`。文件解析器校验 `sample.umi` 和逐帧 `hands` 后，
自动选择 UMI 渲染与提示词。这里的自动选择基于上传件的显式元数据，不是根据数据集名称、`robot_type` 或原始 Zarr 自动发现；
原始会话仍需离线 `export-umi` 和显式标定。`horizon_s` / `--horizon-s` 名称保留，当前含义为历史窗口长度，默认 1 秒。

## 投影与提问

当前帧 t 的历史点（默认 `[t-1s, t]`）均用 `inverse(T_world_camera[t]) @ T_world_eef[t-k]` 投影；不逐帧累加相对动作。使用当前相机的标定和媒体变换，遮掉相机后方的点。画面内不等于没有遮挡。

每路相机仅渲染 `umi.camera_hands` 指定的本手：当前 TCP、接近轴、两指开口和历史轨迹（默认过去 1 秒，到当前帧结束，可配置），不绘制另一只手的几何或开口文字。两手跨视图保持固定配色。本手与腕部相机同帧投影恒定是正常几何关系，不能据此证明世界轨迹正确。模型看到连续视频，判断本手当前投影一致性与已发生的运动/抓放时机；历史轨迹的末端是当前 TCP，早期点重投影到当前相机后不必与过去视频帧中的像素位置相同。另一只手仅作为原始画面中的上下文，不要求它有叠加标记。疑点引用帧号，无法观察则弃权。`aspect=action` 补充原有中心/朝向分类，不改变建议性判决口径。

提示词明确：夹住球、杯沿或杯身时开口通常不为零，持杯倾倒也不要求再次闭合。开合异常必须有可见手指运动的时序证据，不能仅凭非零宽度或物体转移下结论。
松手时机按两指之间实际夹着的那个物体判断，不按它带着走或随它移动的其他物体；松手的时刻是被夹物体不再随相机移动
（夹爪离开时它留在原处），物体还在两指之间就仍是夹着。提示词不写具体物体，适用于任何被夹物。
`/6` 同时整体复查了 UMI 提示词：去掉写死的物体与动作（球、杯沿、倒入），开口与松手合并为一段；说明这是人手持夹爪、
没有机器人指令可比；画面底部印的开口是公制记录值，不与画面估计的物体尺寸比；补上 position / orientation / action 的含义；
任务文本去掉末尾句号再拼接。共用的历史轨迹说明（`history.prompt`，普通 EEF 也用）未改。在这一刻或稍早开口变大、之后保持张开是正常的放下，不算异常；
只有物体明显早于或晚于记录的开口变化离开手指才报时序问题（`umi-action-prompt/6`，2026-10-06：`task-psvkabtjf` 把放下杯子误报为
「球已落杯、夹爪已脱离却仍张开」，置信度 0.88，而画面上帧 1385–1400 杯子仍在两指间、帧 1440 才留在蓝框里）。

普通 EEF 也保留当前 P/A/B 并叠加同一点过去 1 秒的历史（设计 12 §10.5）。两条路径共用 `history.indices` 和
`history.prompt`，统一「历史末端为当前点、历史点使用当前相机投影、缺测不连线」的含义；各自保留标记颜色和任务说明。
当前版本为 `eef-opinion-prompt/3`、`umi-action-prompt/6`，旧缓存不复用。

### 送模型的视频与报告里的叠加（2026-10-06 定）

送模型：叠加视频在内存里逐帧画标记、用 libx264 编码，整段转成 `data:video/mp4;base64,…`，以 Chat Completions 的
`video_url` 内联进请求体（RAW 在前、MARKED 在后，同一请求合计不超过 `max_bytes`）。模型意见的视频长边上限是
`opinion.VIDEO_MAX_SIDE = 448`，不再跟随共用的 `vlm.video.max_side`（720，task_success 仍用它）；复核窗口
（`review.py`，参与判决）暂不改。缓存键里含视频的 sha256 与字节数，分辨率变了旧缓存自然失效。

不落盘：叠加 MP4 与证据帧 JPEG 都不写工作目录，也不上传交付目录。结果记录只留视频元数据（`clips[].video`）和
证据帧号（`segments[].evidence_frames`），不再有 `video_path`、`segments[].evidence`。数据量大了以后，每条 episode
每路相机一段 MP4 会占满本地盘与交付目录，而这些画面随时可以从输入重新画出来。

报告：Episode 明细的模型意见区为每路参与的相机放一个播放器，位于该相机的文字解释之前。播放的是任务输入里该相机的
原始视频（任务级 `VizEpisode` 的相机地址，和迷你播放器同一来源），标记由浏览器在视频上方的 canvas 逐帧画出。
标记来自 `GET /tasks/{id}/episodes/{index}/eef-overlay`（C4 2.6.0 `EefOverlay`）：Daemon 读任务冻结的
trajectory.json（运行目录 `inputs/` 里的副本，工作目录被清理时先从交付目录取回，再不行用上传件本身），
只解析这一条 episode，用和请求同一套选择（`opinion.select`）与投影（`umi.project`、`history.project_eef`、
`review.marks_for`）现场算出每帧的图层，不解码视频，结果按任务、文件与 episode 缓存在内存里。

- 图层：UMI 画本手的过去轨迹、手指连线、接近轴、中心点（手名标签，固定配色）；普通 EEF 画 P 的过去轨迹（青）、
  B（橙）、A（红箭头）、P（红圈）。坐标是原视频像素（`image_size_wh`），每个样本帧一项；过去轨迹最多留约 24 个点，
  缺测处保留断点，不连线。
- 对时：`media_frames[f]` 是样本帧 f 对应的片段内帧号；浏览器用 `(currentTime − from_ts) × fps` 找当前片段帧，
  再反查样本帧，所以 LeRobot v3 一个文件放多条 episode 也对得上。
- 相机对应：按 trajectory.json 里相机的 `media.uri`（LeRobot 的视频文件）或 `media.topic`（mcap）找到播放同一来源的
  `VizEpisode` 相机（`viz_camera`）；找不到时提示原始视频放不了，不画。
- 证据帧：片段下列出帧号按钮，点一下播放器暂停并跳到该帧。
- 与送模型画面的差别：浏览器画的是矢量标记、跟随原视频分辨率，线宽与字号不保证与送模型的像素完全一致；
  标记的位置和内容一致（同一函数算出）。

旧任务里已经落盘的 `opinion/` 视频和图片不再被读取，随工作目录与交付目录原有的清理规则处理。

## 验证

几何检查覆盖参考系变换不变性、当前相机锚定、鱼眼投影、双手独立性和缺测断线。转换检查覆盖视频帧区间、旋转表示、标定缺失及非法 pickle。真实验证集使用 DecisionFacts/Physical-AI-UMI-transfer-objects-from-cups 全部一个 episode、两路相机，保留 VLM 回答和受控异常结果（叠加视频按上节在线画，不再保存）；SLAM 同源信息不作为独立真值。

2026-10-05 初版双手叠加的本地验证（以下模型结论不代表后续仅本手叠加的结果）：plan 与 Zarr 的两手位置、轴角、开口共 1,902 帧逐项吻合（最大误差分别约
`1.5e-8 m`、`1.2e-7 rad`、`3.8e-9 m`）。同一相机的 6–14 秒窗口用
`doubao-seed-2-1-pro-260915`、`reasoning_effort=minimal`、2 fps 视频输入、最终提示词 `umi-action-prompt/2` 做五组对照：

| 输入 | 模型是否报告疑点 |
|---|---|
| 原始数据 | 报告 robot1 位置疑点，尚无独立真值确认 |
| 相机本地 x 外参偏移 40 mm | 否，漏检 |
| 两手轨迹和开口提前 30 帧（约 0.5 秒） | 否，漏检 |
| 两手轨迹和开口互换 | 报告位置疑点 |
| 仅开口提前 30 帧 | 仅报告与原始片段类似的位置疑点，未识别注入的开合错位 |

这是链路与敏感性检查，不是准确率评测。模型解释和区间仍需看视频复核，不能用这几例校准置信度或承诺异常检出率。
早期提示词把非零开口误判成抓取错误；修正语义后，不能把早期回答中的动作疑点当作检出成果。最终模型仍有漏检，
且原始短窗口与整段视频的判断可能不同，因此仅用于辅助复核。
本地原始答复与叠加视频保存在忽略目录 `data/umi-test/anomalies-v2/`，注入脚本为 `data/umi-test/check_anomalies.py`；
CPU 渲染每组约 10 秒，VLM 每组约 11–23 秒（含个别格式修复）。（当时结果页从交付目录签名读取保存的叠加视频；2026-10-06 起改为原视频加在线叠加，见上节。）

初版提示词 `/2` 的完整任务 `task-ujmsisxjc` 成功：两路均保留 1,902 帧 / 31.7317 秒，模型每路接收 RAW 和 MARKED 连续视频，
共两次请求，均返回有效答复、无不匹配片段。模型认为抓放、持杯倾倒与双手配合总体一致，对遮挡及本手世界轨迹保留判断。
任务的通过状态沿用建议性意见规则，不能解读为独立真值验证通过。最终短窗口对照仍有上述漏检与上下文差异。

仅本手、过去 1 秒版本 `umi-action-prompt/5` 的完整任务 `task-iwazpcjgx` 也已成功：同一数据集两路各 1,902 帧、
31.7317 秒，两个真实模型请求均返回有效答复、无不匹配片段。Chrome 中验证报告的两路叠加视频可解码、播放和拖动，
媒体 Range 请求返回 206。`data/umi-test/render_own_hand.py` 生成的两路 MP4 与任务保存的对应视频 SHA-256 完全相同，
配套 `build_preview.py` 可生成独立手动检查页；运行命令见 EEF extension README。
