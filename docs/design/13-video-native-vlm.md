# 连续视频输入与判定（2026-09-24）

任务判定、逐机位复核、取证仲裁、无标注补标和 EEF 模型复核统一使用
Chat Completions `video_url` 输入。本篇取代 04 篇中图片探针的调用图。

## 输入

从数据集的原始相机视频裁出 `[from_ts, to_ts)`，并按 `video.fps` 在窗口起点对齐的均匀网格上
抽帧（每个网格点保留其后第一帧），保留被保留帧的原始 PTS 相对间隔，编码成 H.264 MP4。
本地编码抽帧率与请求里的服务端采样率是同一个配置：模型读到的帧与"全帧编码 + 服务端按该率
抽样"一致，只省掉服务端不会读取的冗余字节——2026-09-24 umi224 的长 episode（166s / 单请求
21.4MB）让 ark 稳定 500，对齐后同窗口仅约 1/6 字节（30fps 源、fps=5）。LeRobot v3 一个文件
可能包含多个 episode，必须先精确裁片，不能直接发送整个文件。
本地文件和 TOS/HTTP 输入走同一裁片路径；远端使用重新签名和有限重试。

每路视频以 `data:video/mp4;base64,...` 发送，带相机名和相对 episode 的时间偏移。
不会把原来抽出的 8 张图片拼成视频。本地编码与服务端共用同一抽帧率；配置明确记录在
`checks.task_success.vlm.video`，打分、复核、仲裁、caption 和 EEF 共用：

```yaml
video:
  fps: 5                  # 本地编码与服务端共用的抽帧率，支持 0.2–5；下调只省字节不改模型可见帧
  max_side: 720           # 本地编码保持宽高比，不放大
  max_bytes: 33554432     # 单次请求所有视频的编码字节总量上限
```

超出字节预算、缺失视频、非法时间窗口或后端不支持视频输入时明确失败，不静默回退图片。
本版完整处理预算内的 episode；超长或高码率 episode 超出预算时进入错误/待复核状态，
没有截断后当成全视频判定。音频不进入机器人视觉质检请求。

## 任务判定

1. 一次请求联合读取多路连续视频，返回 `verdict`、`task_type`、`completion`、`reason` 和 `evidence`。
2. 每路相机独立看自己的完整视频，返回相同结构。
3. 主判和复核有一致成功证据时通过；主判失败且至少一路复核失败、没有成功票时判失败。
   结论冲突或证据不足时弃权。复核成功可以救回不确定的主判。
4. 启用仲裁时，对弃权条目再次核对视频；仲裁成功还需相机复核成功票印证；仲裁失败需要至少两路
   相机复核失败且没有成功票。原始标注的判废继续经过视频 caption 与标注的一致性护栏。

瞬时任务看是否曾真实达成；持久任务看目标状态是否达成并在末态保持。模型看完整过程，
因此取消图片探针、VOC、进度曲线单调性及旧 `success_min`/`fail_max`/`gap_max` 阈值在生产判定中的作用。
历史帧工厂和纯函数只保留供旧交付分析与显式注入的历史测试使用，生产配置工厂始终创建视频客户端。

每条肯定或否定结论必须引用相机及时间段；时间不得超出实际输入窗口。JSON、字段和范围严格校验，
最多一次格式修复。超时和非法回答不会当成失败物证。

完成度为模型估计，保存在 `detail.video_completion`。`task_success` 仍是硬判定模块，不能把估计值
放进通用 `CheckResult.score`，否则会把弃权误记成 `scored`。详情里的痕迹保存视频 hash、窗口、
帧数、主判、复核、仲裁及证据时间段，不保存 Base64 原文。

改标重判同样走视频路径。已有 `relabel_rerun=v1` 值继续表示只做主判和逐机位复核；`full` 表示完整
判定流程，包含仲裁和标注护栏；两者不再选择图片输入协议。

## 补任务描述（原「画像」一节，技能画像已下线，D68）

`caption` 直接读取多机位连续视频，描述机器人尝试的任务；有原始标注时仍以标注为准，补出的描述
只给没有标注的条目用（02 篇 §3.4）。原始标注与视频描述都留着，判废护栏的标注分歧审计读它们。

新 autolabel 记录带 `media_protocol=video-caption/1`。无协议标记的历史图片 caption 不作为新视频
caption 缓存使用；重新执行 autolabel 时也会重做这些条目。`check --resume` 会重新判定缺少当前视频
协议标记的旧探针结果。EEF 的恢复判断同时比较视频协议和预处理配置。

## 逐机位画面缺陷（camera_defects，registry 1.14）

逐机位复核的请求里追加一段提问，让模型在返回成败结论的同一份 JSON 里多给一个字段 `camera_check`，
报告这路相机自己的三项画面缺陷：花屏（`glitch`）、相机抖动（`shake`）、镜头污染（`contamination`）。
每项给 `none` / `minor` / `severe` / `unknown` 四档、若干时间段（口径同 `evidence`：episode 相对秒）
和一句说明，污染另给 `kind`（`dirt` / `smudge` / `water` / `obstruction` / `other`）。抖动指相机本体
晃动，腕部相机随手臂运动属正常，只报超出的抖动。

- **不增加模型调用**：复核请求本来每路相机一次、无条件发出，这段提问只是让同一次回答多带一个字段。
  请求体不变（没有新媒体），只多约 150 个输出 token。
- **每次都问**，没有开关、界面上也不勾选：`camera_defects` 是 `task_success` 的随附模块
  （`ModuleSpec.rides_on="task_success"`）。凡是 `task_success` 在跑，它就出结果；单独跑它是参数错误。
- **只出结果，不影响判决**：`affects_dataset_verdict=False`，记录永远是 `passed=score=null`（`abstain`），
  不进 keep / drop / held，不提复核问题。注册表 2.0（设计 17，2026-10-01）去掉了这个字段：三个细码 `glitch`（IMG-5）、
  `shake`（IMG-6）、`contamination`（IMG-7）默认级别都是 info，效果相同；它骑在任务成败判定的请求上（`rides_on`），从不单独待补跑，
  模型没回答（unknown）在记录 2.0 里是 unassessable `model_no_answer`。
- **解析永不失败**：缺字段、档位写错、时间段越界都只记进 `problems`，三项按 `unknown` 落盘，绝不触发
  格式修复重试，也不影响 `verdict`、`completion` 和 `evidence` 的校验。
- **写坏了也只赔自己**：整份回答解析不了时，先按花括号配对把 `camera_check` 这一个字段整块剪掉再解析
  五个核心字段；剪成功照常出判决，三项记 unknown 并写明原因，剪不掉才按老规矩修复重试。2026-09-28
  真实数据上模型写出 `"times":[[2,5] [9,12]]`（漏逗号），此前会让整路复核失败、把 episode 拖成待补跑。
- **约束解码**：三类视频调用（主判、复核、仲裁）都带 `response_format: {"type": "json_object"}`，由服务端
  保证输出是合法 JSON，从根上消掉语法错误这一类；后端拒绝这个字段时自动降级为不带它再问（自建引擎不一定
  支持），不因此失败。语义仍靠既有校验：引用的相机、时间窗口、档位枚举照旧检查，一次修复重试保留。
- **整段就说整段**：覆盖窗口 95% 以上的时间区间折成 `whole` 标记、清空 `times`，控制台显示「全程」。
  5fps 下模型的定位精度只有 0.2 秒且会四舍五入，一个 0–57 秒的区间是「一直都有」而不是定位，不该写成
  看起来精确的数字。每项最多两个区间，取最严重的两段，本质是线索而非穷举。
- 记录的 `details`：`protocol="camera-check/1.1"`、`source="task_success.video_reviews"`、`items` 是三项各一个
  跨机位最坏档（`none` / `minor` / `severe` / `unknown`），逐机位的档位、时间段与污染种类只存一份在
  `per_camera` 里（同一件事不说两遍），`clean_ratio` 是「已答项里判为 none 的比例」，`reason` 说明为什么是
  unknown（成败判定没结果 / 没跑复核 / 模型没答）。报告小节按三项各一张计数图，episode 明细页一行给三项
  最坏档、再只列报了问题的机位。
- `--resume` 口径：`details.protocol` 不是当前协议号的旧记录视为待补跑，会连同 `task_success`
  一起重判；主判协议 `video-task/1` 不动。**改了这一段的措辞就要把协议号升一版**（`camera-check/1`
  → `1.1`，2026-10-07：区分花屏与抖动、最多四段、能写 intermittent）—— 不升的话旧 prompt 判出来的
  记录和新的长得一样，重试不会重判，一个任务里会掺着两套措辞的答案而看不出来。
- 模型在 5fps / ≤720p 上可能漏掉单帧花屏、把腕部相机的正常运动当抖动、把静止遮挡物当污染——所以它只
  作建议项，与 CPU 侧 `visual_quality`（清晰度、曝光、冻结的逐帧统计量）互补。

## EEF 复核

每个复核窗口发送两段连续视频：RAW 原图和 MARKED 投影叠加图。保留原视频时间轴；叠加图按每一帧
对应的轨迹样本绘制 P/A 和跟踪点，没有映射样本的帧明确标识且不伪造投影。
输出仍是位置/方向等分类与合法证据帧号，数值测量由原有 CPU 几何链路负责。
报告保留静态局部证据图，但模型输入使用视频。缓存键包含视频字节 hash、prompt 和采样配置。

## 验证和适用范围

离线测试用真实 H.264 小视频检查裁片边界、连续帧和 PTS，用 HTTP 桩和录制回放验证各生产入口的
`video_url` 请求、输出校验、错误处理、改标重判和 EEF。新的录制带对视频字节做 hash，避免
把 Base64 视频复制进 tape。

这些验证不等于真实模型质量校准。模型误杀/漏放、人工复核比例、吞吐和成本仍需用人工标注集做在线
对照；planner 的视频请求次数已更新，耗时暂用带“未校准”说明的历史请求基线。

## 模型选型记录

出厂默认见 `pipeline/default.yaml` 的 `checks.task_success.vlm.model`（模型只在这一处配置）。
选型依据随实测更新，换模型前先重跑本节的在线对照。

- **2026-09-24 定 doubao-seed-2-1-pro-260915（reasoning_effort=minimal）**，umi224（7 条，
  最长 166s 双相机）实测：
  - glm-5-3-flash-260828：对 ep4/ep5 稳定 500（4 次重试全挂）；本地抽帧把请求降到 7.2MB 后依旧，
    且其 1024k 规格窗口远未用满——属该模型在方舟上对长视频输入的实现问题，非规格限制，
    方舟工单 request id 见运维记录；其思考不可关，可能与长输入处理冲突。
  - doubao-seed-2-0-pro-260215：能跑通，但单请求 119k prompt 已用其 224k 输入上限的 53%，
    更长/更多相机的 episode 会顶到。
  - doubao-seed-2-1-pro-260915：1024k 输入余量充足；四连跑判决完全稳定（3/4 遍逐条一致，
    边界样本 ep2 一次 keep 三次 drop，与 2.0-pro 的 drop 交叉印证）；冷跑速度与 2.0-pro 相当
    （~295s/7 条），重复跑因方舟 prompt 缓存快 4 倍（缓存命中与视频字节相同直接相关）。
- 视频输入规格（方舟，Seed 系与 GLM 同口径）：单视频 ≤1280 帧、≤80k token（帧 64–384 token
  动态，720p 实测 ~72 token/帧）；Base64 请求体 ≤64MB。fps=5 时长天花板由 80k token 决定
  ≈3.7 分钟/路，超过就降 fps（时长 × fps × 72 ≤ 80000）。

接口参考：[火山方舟视频理解](https://www.volcengine.com/docs/82379/1895586)。
