# 连续视频输入与判定（2026-09-24）

任务判定、无标注补标和 EEF 模型复核统一使用
Chat Completions `video_url` 输入。本篇取代 04 篇中图片探针的调用图。

## 输入

从数据集的原始相机视频裁出 `[from_ts, to_ts)`，并按 `video.fps` 在窗口起点对齐的均匀网格上
抽帧（每个网格点保留其后第一帧），保留被保留帧的原始 PTS 相对间隔，编码成 H.264 MP4。
本地编码抽帧率与请求里的服务端采样率是同一个配置：模型读到的帧与"全帧编码 + 服务端按该率
抽样"一致，只省掉服务端不会读取的冗余字节——2026-09-24 umi224 的长 episode（166s / 单请求
21.4MB）让 ark 稳定 500，对齐后同窗口仅约 1/6 字节（30fps 源、fps=5）。LeRobot v3 一个文件
可能包含多个 episode，必须先精确裁片，不能直接发送整个文件。
本地文件和 TOS/HTTP 输入走同一裁片路径；远端使用重新签名和有限重试。

每路视频以 `data:video/mp4;base64,...` 发送，带相机名和相对 episode 的时间偏移。
不会把原来抽出的 8 张图片拼成视频。本地编码与服务端共用同一抽帧率；配置明确记录在
`checks.task_success.vlm.video`，判定、caption 和 EEF 共用：

```yaml
video:
  fps: 5                  # 本地编码与服务端共用的抽帧率，支持 0.2–5；下调只省字节不改模型可见帧
  max_side: 720           # 本地编码保持宽高比，不放大
  max_bytes: 33554432     # 单次请求所有视频的编码字节总量上限
```

超出字节预算、缺失视频、非法时间窗口或后端不支持视频输入时明确失败，不静默回退图片。
本版完整处理预算内的 episode；超长或高码率 episode 超出预算时进入错误/待复核状态，
没有截断后当成全视频判定。音频不进入机器人视觉质检请求。

## 任务判定（D71，2026-10-07：一次判决）

1. **一次请求**联合读取多路连续视频，返回整条的 `verdict`、`task_type`、`completion`、`reason`、`evidence`，
   **以及每路相机各自的结论**（`cameras`：这一路单独看到了什么，成功 / 失败 / 不确定，连同它的画面缺陷）。
2. 通过 = 整条判成功且没有相机说失败；判废 = 整条判失败、至少一路相机说失败、没有相机说成功，且引用了物证
   （解析器拒绝没有物证的确定结论）。**其余一切不够确定的直接转人工**。
3. 没有逐机位复核请求、没有取证仲裁：同一个模型、同一段视频、温度 0，再问一次得到的是同一个意见，不是第二个。
   相机的结论出自同一次推理，所以不当作独立的第二签，只用来「不能自相矛盾」。
4. ~~原始标注的判废继续经过视频 caption 与标注的一致性护栏~~ D73 起没有判废护栏：判废就是那一次回答和它引用的证据，
   每条有标注的条目恰好 1 次请求。没有标注的条目同样 1 次：只问画面缺陷（`CAMERAS_ONLY_PROMPT`），不问成败。

改之前（2026-09-24 至 2026-10-07）是两段式 `video-task/1`：主判一次、每路相机各复核一次、判废要双签、冲突再仲裁。
需求方 2026-10-07 定为单次判决，没有开关；那套代码留给 v1 的 `rejudge`，v2 不再建复核与仲裁的客户端。

瞬时任务看是否曾真实达成；持久任务看目标状态是否达成并在末态保持。模型看完整过程，
因此取消图片探针、VOC、进度曲线单调性及旧 `success_min`/`fail_max`/`gap_max` 阈值在生产判定中的作用。
历史帧工厂和纯函数只保留供旧交付分析与显式注入的历史测试使用，生产配置工厂始终创建视频客户端。

每条肯定或否定结论必须引用相机及时间段；时间不得超出实际输入窗口。JSON、字段和范围严格校验，
最多一次格式修复。超时和非法回答不会当成失败物证。

完成度为模型估计，保存在 `detail.video_completion`。`task_success` 仍是硬判定模块，不能把估计值
放进通用 `CheckResult.score`，否则会把弃权误记成 `scored`。详情里的痕迹保存视频 hash、窗口、
帧数、整条与逐机位的结论及证据时间段，不保存 Base64 原文。

改标重判同样走视频路径。D39 的 `relabel_rerun` 两种口径（`v1`：主判加逐机位复核；`full`：完整流程）在
单次判决下没有区别了——改了标的条目都是用新描述发一次判定请求；字段与对话框暂留，行为合一。

## 视频描述（原「画像」一节；技能画像 D68、补任务描述 D72、判废护栏 D73 已下线）

`caption`（`dataset_level/caption.py`）直接读取多机位连续视频，描述机器人尝试的任务。v2 的判定流程已不再调它：
没有标注的条目不补描述、不判成败，只发一次画面缺陷请求（02 篇 §3.4）；判废前也不再拿画面描述核对标注。代码留给 v1。
`check --resume` 会重新判定缺少当前视频协议标记的旧探针结果。EEF 的恢复判断同时比较视频协议和预处理配置。

## 逐机位画面缺陷（camera_defects，registry 1.14；7.2 加遮挡与机位身份）

判定请求里每路相机的回答各带一个字段 `camera_check`（D71 之前是追加在逐机位复核请求上），
报告这路相机自己的四项画面缺陷：花屏（`glitch`）、相机抖动（`shake`）、镜头污染（`contamination`）、
视觉遮挡（`occlusion`，注册表 8.1 起）。每项给 `none` / `minor` / `severe` / `unknown` 四档、若干时间段
（口径同 `evidence`：episode 相对秒）和一句说明，污染另给 `kind`（`dirt` / `smudge` / `water` / `obstruction` / `other`）。

**每一项的措辞都卡在它那一个检测项里**（`camera-check/10`）：四项在分类表（C6 2.0）里是互斥的，各自写了与邻项的判别法，
提示词把这些判别法照搬过去，否则答回来的证据会以发问那个细码的名义落在错的项上：

| 项 | 判别法写进提示词的说法 | 不这么说会落到 |
|---|---|---|
| IMG-5 花屏 | 是录下来的画面本身坏了；糊、拖影、失焦不算，画面只是不动也不算 | IMG-4 模糊失焦、IMG-1 画面冻结 |
| IMG-6 相机抖动 | 骑在手上的相机跟手走不算；松动引起的发抖算（分类表原文就写了支架松动）；动一次就停在新角度不算 | IMG-12 相机移位 |
| IMG-7 镜头污染 | 脏东西在镜头上，跟着相机走、始终盖着画面同一块；随场景漂移或从镜头前经过的是遮挡 | IMG-8 视觉遮挡 |
| IMG-8 视觉遮挡 | 镜头与场景之间的东西挡住作业区；对着别处、根本没拍到不算 | IMG-13 物体出画 |

**遮挡另给三个数**（需求方 2026-10-12）：`source`（挡住画面的是什么：`arm` / `body` / `person` / `object` / `cable` /
`other`）、`coverage`（最严重时遮住画面的比例，0–1）、`region`（遮挡物在画面里的位置：`left` / `right` / `top` /
`bottom` / `center` / `whole`）、`duration_s`（这路相机被挡住的总秒数）；`share`（时长占窗口的比例）由解析算出，
给控制台一行读数用。模型没给或给得不合法时，解析按已知的时间段补：有 `whole` 或没给时间段就按整段算，`none` 记 0。

**什么不算遮挡**（提示词里逐条写明，都是实测踩过的误报）：光照变化（关灯、阴影、自动曝光——整幅画面一起变，
而且三路相机同时变，真遮挡只出现在一路）；机器人自己的手臂、夹爪、手里搬的东西，哪怕占满画面，那是任务本身；
人、手或物件只是**在场景里**（操作台前干活的人也算），只有挡在镜头与操作区之间才算；画面暗、空、离操作区远或
对着别处——没有东西盖住它。遮挡与花屏的分界：画面其余部分完整清晰、只有一块被盖住是遮挡（东西在镜头前），
画面内部坏掉（色块、撕裂、拖影）是花屏，同一段绝不两项都报。贴在镜头上的东西算污染不算遮挡。

同一个字段里还有一项 `view`（4.1 起）：模型只看画面说这路相机**物理上是什么**——`kind`（`wrist` 随臂运动、
`fixed` 场景不动）、`arm`（装在哪条臂上或主要看哪条臂，单臂机器人 `single`）、`matches_name`（画面是否与相机的命名
相符：命名里带 wrist / hand / gripper 却是固定机位、固定命名却随臂动、双臂机器人命名里的 left / right 与画面相反，
才答 `no`；单臂机器人或双目的 left / right 与臂无关，答 `unknown`）。
**身份一致是「画面对数据集的说法」，不是「画面对相机名字」**（`camera-check/6`，2026-10-13）。
第一轮在 FastUMI 上空转，就是因为只给了名字：那套设备两路腕部相机、没有外部视角，每路画面里基本只有自己这只夹爪，
模型答「单臂」，再被「单臂的 left / right 与臂无关」挡掉，46/48 路记成未知。平台手上本来就有依据，只是没送进请求：

- **几条臂、叫什么**：数据集自己的动作 / 状态通道名（FastUMI 是 `left_x … left_gripper, right_x … right_gripper`，
  就是两条臂；DROID 的 `x,y,z,roll,pitch,yaw,gripper` 没有臂前缀，就是一条）。`robot_type` 常常是空的，不靠它。
- **每路相机是什么**：数据集声明（C7 `dataset-declaration/1.0`，设计 25）的 `calibration.cameras[*]`：`mount`
  （`wrist` / `fixed_external`）与 `owner`（哪只手 / 哪条臂）。任务开跑时冻进 `run.json`，`check` 本来就收 `--declaration`。

`pipeline/dataset_claim.py` 把这两样拼成一段话，随判定请求（和无标注条目那个只问画面缺陷的请求）发出去：
「这台机器人有 2 条臂，数据集的通道名叫 left 和 right；数据集声明 X 是左手的腕部相机、Y 是固定第三视角」。
模型的活儿因此变成**比对**：`view.matches_name` 是「你看到的」对「数据集说的」，矛盾才答 `no`；数据集没说就答 `unknown`——
这时的 unknown 是诚实的「没有可比的东西」。数据集什么都没说时这段话不发，请求和以前一样。

**左右臂串线**（`arms`）不问模型，改成在 CPU 上量。腕部相机是拧在手上的：那只手一动，整幅画面跟着晃；另一只手动，它不晃。
数据集两只手的动作都记着，所以「这路相机骑在哪条臂上」是个可测量，不是判断题。`pipeline/arm_pairing.py` 每条 episode 三步：

1. 逐样本算**画面自己的位移**——把帧缩成 160 像素宽的灰度图做相位相关，不认物体、不认特征，一帧几毫秒；
2. 逐样本算**每条臂的速度**——`dataset_claim` 已按通道名把列分好（夹爪那一列不算：夹爪开合不晃相机）；
3. 只看**一条臂单独在动**的时刻：它在自己速度的前四分之一，别的臂在后一半且当时至少慢一倍。两只手一起动的时刻什么也说明不了，丢掉。
   每路相机对每条臂给一个读数：那些时刻里画面走的距离 ÷ 那条臂走的距离，因此一条臂忙一条臂闲也能比。

最后**整条 episode 只做一次配对**：两路相机配两条臂只有两种配法（照名字、或对调），各按读数打分，赢的一种还要赢出余量才算数。
按相机各自挑臂会出现两路都挑同一条臂的自相矛盾——当时 4 条错答里有 3 条是这么来的。相机实际骑的臂不是数据集给它的那条就是串线；
差距不够就答 `unknown`：假的「一致」会把坏数据集盖过去，`unknown` 只多报告一行。

实测 `anchor-arms-fastumi`（14 条按像素规则确认两路相机文件对调，10 条样本集没标出问题）：对调抓到 12 条、2 条 unknown；
干净的 8 条答一致、1 条 unknown、1 条误报成对调；48 个视频合计 11 秒，不发一次模型请求，也没有把对调的答成「一致」——
那才是真正要避免的错。同一批数据问模型（`camera-check/7` 那版提问）只认出 1 条、24 条里弃权 20 条：证据本身太弱，
手持夹爪时另一只夹爪在模型收到的 720×404 画面里只有二十来个像素，还贴在鱼眼圆边上；需求方 2026-10-13 定了不为此额外补图。
所以这一问从提问里整段拿掉（`camera-check/8`），模型只答画面真能看出来的：`view.kind`（腕部 / 固定，看画面是否随臂摆动）、
`view.matches_name`（只比**安装方式**与数据集声明是否矛盾，不许因为「我觉得它在哪条臂上」答 `no`）。`view.arm` 腕部相机一律答
`unknown`——哪条臂由上面量出来。

`camera_defects` 由此给每条 episode 一个 `identity`：有一路 `no` / `same_as`，或量出 `crossed`，就是 `inconsistent`；
有一路 `yes` 或量出 `consistent` 且无人反对是 `consistent`；两边都没说是 `unknown`。细码 `identity`（MV-2，info）
按机位各报一条，串线另报一条（范围是涉及的几路相机）。

- **不增加模型调用**：判定请求本来每条 episode 一次、无条件发出，这段提问只是让同一次回答多带一个字段。
  请求体不变（没有新媒体），只多约 150 个输出 token。左右臂配对走 CPU，也不发请求：本机 FastUMI 两路 720p
  约 0.5 秒一条，视频用的还是这一档已经打开的那份（远端走 episode 的共享块，不额外下载）。
- **每次都问**，没有开关、界面上也不勾选：`camera_defects` 是 `task_success` 的随附模块
  （`ModuleSpec.rides_on="task_success"`）。凡是 `task_success` 在跑，它就出结果；单独跑它是参数错误。
- **只出结果，不影响判决**：`affects_dataset_verdict=False`，记录永远是 `passed=score=null`（`abstain`），
  不进 keep / drop / held，不提复核问题。注册表 2.0（设计 17，2026-10-01）去掉了这个字段：细码 `glitch`（IMG-5）、
  `shake`（IMG-6）、`contamination`（IMG-7）、`occlusion`（IMG-8）、`identity`（MV-2）默认级别都是 info，效果相同；它骑在任务成败判定的请求上（`rides_on`），从不单独待补跑，
  模型没回答（unknown）在记录 2.0 里是 unassessable `model_no_answer`；MV-2 的左右臂配对是实测，量不出结论记
  `measurement_inconclusive`、数据集没有可比的两条臂记 `not_applicable`（注册表 8.1），不记成「模型没答」。
- **解析永不失败**：缺字段、档位写错、时间段越界都只记进 `problems`，三项按 `unknown` 落盘，绝不触发
  格式修复重试，也不影响 `verdict`、`completion` 和 `evidence` 的校验。
- **写坏了也只赔自己**：整份回答解析不了时，先按花括号配对把 `camera_check` 这一个字段整块剪掉再解析
  五个核心字段；剪成功照常出判决，三项记 unknown 并写明原因，剪不掉才按老规矩修复重试。2026-09-28
  真实数据上模型写出 `"times":[[2,5] [9,12]]`（漏逗号），此前会让整路复核失败、把 episode 拖成待补跑。
- **约束解码**：判定请求带 `response_format: {"type": "json_object"}`，由服务端
  保证输出是合法 JSON，从根上消掉语法错误这一类；后端拒绝这个字段时自动降级为不带它再问（自建引擎不一定
  支持），不因此失败。语义仍靠既有校验：引用的相机、时间窗口、档位枚举照旧检查，一次修复重试保留。
- **整段就说整段**：覆盖窗口 95% 以上的时间区间折成 `whole` 标记、清空 `times`，控制台显示「全程」。
  5fps 下模型的定位精度只有 0.2 秒且会四舍五入，一个 0–57 秒的区间是「一直都有」而不是定位，不该写成
  看起来精确的数字。每项最多两个区间，取最严重的两段，本质是线索而非穷举。
- 记录的 `details`：`protocol="camera-check/10"`、`source="task_success.cameras"`、`items` 是四项各一个
  跨机位最坏档（`none` / `minor` / `severe` / `unknown`），`identity` 是整条的机位身份结论，`arms` 是量出来的左右臂配对
  （`identity` / `crossed` / `basis="motion_pairing"` / `readings`：各臂单独在动的时刻数、每路相机对每条臂的读数、赢出的余量），
  逐机位的档位、时间段、污染种类、遮挡的来源 / 比例 / 位置 / 时长、`view` 只存一份在 `per_camera` 里（同一件事不说两遍），
  `clean_ratio` 是「已答项里判为 none 的比例」，`reason` 说明为什么是 unknown（成败判定没结果 / 没跑复核 / 模型没答）。
  报告小节按四项各一张计数图加一张机位身份计数，另给遮挡的总秒数与最大遮挡比例；episode 明细页一行给四项最坏档
  （遮挡带比例、位置、时长），再只列报了问题的机位，机位身份不符或左右臂串线时另起一行说哪一路、画面是什么。
- `--resume` 口径：`details.protocol` 不是当前协议号的旧记录视为待补跑，会连同 `task_success`
  一起重判。**改了这一段的措辞就要把协议号升一版**（`camera-check/1` → `1.1`：区分花屏与抖动、最多四段、
  能写 intermittent；→ `2`：随 D71 搬进判定请求的逐机位回答；→ `3`：加遮挡与 `view`；→ `4`：遮挡与操作本身、
  与花屏分不清，机位种类照着命名抄；→ `5`：需求方 2026-10-12 复核样本后，逐条写明什么不算遮挡（光照、场景里的人与物、
  对着别处的画面），遮挡另出比例、位置与时长，并加上左右臂跨相机串线的提问；→ `6`：身份一致改成对照数据集的说法
  （通道名给臂、声明给相机），不再只对相机名字；→ `7`：第一轮在 anchor-arms-fastumi 上 14 条对调只认出 1 条、12 条答了「一致」，
  措辞改成「本机位自己的夹爪永远在画面下方固定不动，不作数；要沿左右边缘找另一只」，并写明方向（左手的相机在自己画面偏右看到另一只，
  实测 ep0 对调 / ep14 正常两边都验证过），同时规定没真看到就只能答 unknown，不许凭名字答一致；→ `8`：这一问整段拿掉，
  左右臂配对改成 CPU 实测（见上），模型那边只留安装方式的比对；→ `9`：抖动与遮挡按**手持机位**重写——相机在人手里，
  跟着手走多大都不算抖动（只报手的运动解释不了的：磕碰、高频抖、夹爪不动画面还在晃、机位松了），拿着夹爪的那只手和前臂
  算机械臂、不算路人，手里的东西占满近景就是在干活。改之前这 24 条无缺陷的 FastUMI 上报了 6 条抖动、3 条遮挡，
  说明文字写的正是这两件事；→ `10`：每一项的措辞卡回它自己那一项（见上表），并去掉 `view.same_as`——
  「两路是同一份录像」没有任何检测项要求，它以 MV-2 的名义报了 MV-2 不管的事）—— 不升的话旧 prompt 判出来的记录和新的
  长得一样，重试不会重判，一个任务里会掺着两套措辞的答案而看不出来。`5` 之前的记录没有遮挡的三个数与 `arms`：
  读出来 IMG-8、MV-2 记 unassessable，不报错。
- 模型在 5fps / ≤720p 上可能漏掉单帧花屏、把腕部相机的正常运动当抖动、把静止遮挡物当污染、把机械臂正常经过
  镜头前当遮挡——所以它只作建议项，与 CPU 侧 `visual_quality`（清晰度、曝光、冻结的逐帧统计量）互补。机位身份
  只在画面明显与命名矛盾时才说不符，单臂与双目命名里的 left / right 一律不作判断，宁可 unknown。

## EEF 复核

每个复核窗口发送两段连续视频：RAW 原图和 MARKED 投影叠加图。保留原视频时间轴；叠加图按每一帧
对应的轨迹样本绘制 P/A 和跟踪点，没有映射样本的帧明确标识且不伪造投影。
输出仍是位置/方向等分类与合法证据帧号，数值测量由原有 CPU 几何链路负责。
报告保留静态局部证据图，但模型输入使用视频。缓存键包含视频字节 hash、prompt 和采样配置。

## 验证和适用范围

离线测试用真实 H.264 小视频检查裁片边界、连续帧和 PTS，用 HTTP 桩和录制回放验证各生产入口的
`video_url` 请求、输出校验、错误处理、改标重判和 EEF。新的录制带对视频字节做 hash，避免
把 Base64 视频复制进 tape。

这些验证不等于真实模型质量校准。模型误杀/漏放、人工复核比例、吞吐和成本仍需用人工标注集做在线
对照；planner 的视频请求次数已更新，耗时暂用带“未校准”说明的历史请求基线。

## 模型选型记录

出厂默认见 `pipeline/default.yaml` 的 `checks.task_success.vlm.model`（模型只在这一处配置）。
选型依据随实测更新，换模型前先重跑本节的在线对照。

- **2026-09-24 定 doubao-seed-2-1-pro-260915（reasoning_effort=minimal）**，umi224（7 条，
  最长 166s 双相机）实测：
  - glm-5-3-flash-260828：对 ep4/ep5 稳定 500（4 次重试全挂）；本地抽帧把请求降到 7.2MB 后依旧，
    且其 1024k 规格窗口远未用满——属该模型在方舟上对长视频输入的实现问题，非规格限制，
    方舟工单 request id 见运维记录；其思考不可关，可能与长输入处理冲突。
  - doubao-seed-2-0-pro-260215：能跑通，但单请求 119k prompt 已用其 224k 输入上限的 53%，
    更长/更多相机的 episode 会顶到。
  - doubao-seed-2-1-pro-260915：1024k 输入余量充足；四连跑判决完全稳定（3/4 遍逐条一致，
    边界样本 ep2 一次 keep 三次 drop，与 2.0-pro 的 drop 交叉印证）；冷跑速度与 2.0-pro 相当
    （~295s/7 条），重复跑因方舟 prompt 缓存快 4 倍（缓存命中与视频字节相同直接相关）。
- 视频输入规格（方舟，Seed 系与 GLM 同口径）：单视频 ≤1280 帧、≤80k token（帧 64–384 token
  动态，720p 实测 ~72 token/帧）；Base64 请求体 ≤64MB。fps=5 时长天花板由 80k token 决定
  ≈3.7 分钟/路，超过就降 fps（时长 × fps × 72 ≤ 80000）。

接口参考：[火山方舟视频理解](https://www.volcengine.com/docs/82379/1895586)。
