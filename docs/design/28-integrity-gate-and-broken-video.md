## 0. 开工指引

1. 判决不变：完整性判废的条目照旧因完整性的发现判废；这一期改的是其它模块在这些条目上做不做、怎么记，以及坏视频算发现还是算出错。
2. 顺序（每一步 CI 都能绿）：契约（注册表 7.1、C2 可选字段、C4 7.1.0）→ CLI 的拦截与坏视频 → Daemon 的等待 → 报告与控制台的记账 → 文档。
3. 不动的：完整性模块本身（逐帧解码测试仍默认关）；EEF 模块（它从不判废，读不了的视频照旧记执行出错，见 §2.4）。

## 1. 完整性拦截（D92）

**拦谁**：任务选了数据完整性，完整性对一条 episode 的记录里有按任务策略为 blocking 的发现（`run.json` 冻结的策略；`report_only` 下完整性的
blocking 照样是 blocking，策略版本 2）。review 级的「完整性存疑」不拦，它们照常交给后面的模块。

**谁拦**：`curation check` 自己。每条 episode 动手之前先看完整性对它的记录（运行目录里的分片；流水线下也是同一份分片，完整性的工人写完才交接）。
判废了就不读这条的数据、不解码、不调模型，给这次调用的每个所选模块写一条**跳过记录**：

```jsonc
{"episode_index": 30, "module": "timestamp_check", "status": "ok",
 "findings": [], "assessed": [],
 "unassessable": [{"item": "STRM-3", "reason": "integrity_rejected", "text": "数据完整性已判废，没有评估"}, …],   // 本模块覆盖的每一项
 "readings": {},
 "details": {"skipped": "integrity_rejected", "reason": "数据完整性已判废：数据不合规：ep000030: action 含 35 个 NaN/Inf"},
 "evidence": [], "elapsed_s": 0.0, "error": null}
```

完整性还没有这条的记录（没选完整性、完整性整体失败、手工跑时还没跑完整性）就照常判，不等。

**Daemon 的顺序**：CPU 块里完整性本来就在最前面，后面的段拿到的条目都已有完整性的结论。VLM 块的链（`vlm_prep → vlm`，或只有 `vlm`）
和完整性并排开跑，所以它的第一段要等：一条 episode 的完整性有了结论才派发。「有了结论」指在完整性所在的那条链上，这条已经过了完整性那一段
（写了记录、缺源文件被跳过，或完整性整体失败被放行）。没选完整性就不等。完整性很快（droid200 46 条约 18 秒，只读文件头尾），模型块只是开头晚几秒。

**判决与重试**：跳过记录没有发现、不是出错，所以这条只因完整性的发现判废，拒绝理由里不再挂一串「另有…执行出错」。重试只补出错或缺记录的
（模块 × 条目），跳过的条目两样都不是，不会被重跑。完整性的判废发现不可复议（现在就是），不会出现「复议恢复了、其它模块却没结论」的情况。
完整性「存疑」被人判成「坏了」的，其它模块当时已经跑过，照常。

**EEF 的两半**：CPU 半段（`vlm_prep`）碰到判废的条目直接写跳过记录，不留请求包；模型半段再见到它时同样写跳过记录（内容相同）。

## 2. 坏视频是判废发现（D93）

### 2.1 认定

解码时报下面这些，是文件本身坏了，换个时间重读结果一样：

- PyAV 的 `InvalidDataError`（FFmpeg 的 AVERROR_INVALIDDATA，原话 `Invalid data found when processing input`）；
- 容器里找不到 `moov`，或找不到视频流。

网络错误、超时、HTTP 5xx、对象读不到（404 归 D40 的缺源文件）、内存不足、进程崩溃，仍是执行出错（D33 原口径），进待补跑。

### 2.2 谁报、怎么报

视觉质量、视频-动作同步（帧段同一次解码）和任务成败判定（准备视频）遇到 §2.1 的错误，各报一条发现：

| 细码 | 检测项 | 级别 | 可复议 | 范围 | 读数 |
|---|---|---|---|---|---|
| `decode_failed` | FILE-4 视频解码失败 | blocking | 否 | 坏的那一路相机 | 解码器原话（截到 200 字） |

记录是 `status: ok`；本模块其它项记无法评估，理由 `video_undecodable`（「视频解不开（文件损坏）」）。几路相机里只有一路坏的，帧段照旧给出
能算的读数和发现，再加这一条；任务成败判定一次请求要全部机位，坏一路就不发请求。

### 2.3 镜头画面缺陷

它随任务成败判定那一次请求作答（D73）。请求没发，三项（IMG-5、IMG-6、IMG-7）记无法评估 `video_undecodable`，记录 `status: ok`。

### 2.4 不在这一期

- EEF 模块：从不判废（D81），读不了的视频照旧记执行出错。这样的条目一般已被别的模块因 `decode_failed` 判废（D35：判废压过出错）；只选了 EEF
  的任务里它会待补跑，留到第二期。
- 完整性开了逐帧解码测试时，它与这三个模块会各报一条，拒绝理由里同一个原因出现几次，可以接受。

### 2.5 覆盖

三个模块的覆盖多一项 FILE-4，意思是「按它们读到的帧，视频解得开」：视觉质量与同步按抽帧读，任务成败判定读整段送模型的片段。报告的检测项覆盖
因此在没开逐帧解码时也会把 FILE-4 标成覆盖。回归样本的平台注记按注册表重新生成。

## 3. 「跳过」单独记账（D94）

**跳过记录**：`details.skipped` 有值的记录，现在有两种：`no_task_text`（D72，没有任务标注，任务成败不判）和 `integrity_rejected`（D92）。
它们 `status: ok`、没有执行出错，但模块没有评估这一条。之前它们混在「评估」里，`no_task_text` 还被算成「弃权（转人工）」，这一期分开：

| 地方 | 改成 |
|---|---|
| 判定词（`records.legacy_verdict`） | 新词 `skipped`，报告的 `counts` 与模块视图按它数 |
| 报告模块小节（C2 report） | `assessed_episodes` 不数跳过；summary 多 `skipped_episodes` 与 `skipped_reasons`（`[{name, count}]`，`name` 是跳过的理由）；`counts` 多 `skipped` |
| 任务成败小节 | 判定结论分布、弃权原因、「转人工」都不数 `no_task_text` |
| `report.md` | 模块行「评估 N 条；跳过 M 条（数据完整性已判废 K）；检出：…」 |
| `check --json`（C2 check） | 每个模块多 `skipped`（条数） |
| 任务详情的模块卡片（C4 `PipelineEpisodes.modules[]`） | 多 `skipped`；`judged` 不含跳过 |
| 控制台 | 模块卡片、报告小节写「跳过 M 条」，悬停或小字说明原因 |

## 4. 契约

- **C1 → 7.1**（只加）：`visual_quality`、`video_action_sync`、`task_success` 各加细码 `decode_failed`（FILE-4，blocking，不可复议），覆盖随之多
  FILE-4；无法评估的理由加 `integrity_rejected`（「数据完整性已判废，没有评估」）与 `video_undecodable`（「视频解不开（文件损坏）」）。
- **C2**：结果记录的形状不变，`details.skipped` 的取值写进说明；`check` 每个模块多可选的 `skipped`；报告模块小节多可选的 `skipped_episodes`、
  `skipped_reasons`，`counts` 多可选的 `skipped`。都是可选字段，`schema_version` 不变。
- **C3**：不变。
- **C4 → 7.1.0**：流水线模块计数多 `skipped`；变更记录（中英）写「完整性判废的条目其它模块不再评估，单列为跳过；损坏的视频判废」。

## 5. 验收

1. CLI：在合成夹具上弄坏几条（空文件、NaN、时间戳倒退、视频流中段损坏），按段跑：数值、画面、重复检测、任务成败都不在完整性判废的条目上读数据，
   给它们写跳过记录；视频流中段损坏的条目由视觉质量、同步、任务成败各报 `decode_failed`，判废、不进待补跑；模拟一次超时仍进待补跑。
2. Daemon：VLM 块等完整性的结论再派发；完整性整体失败时不等；编排用例覆盖等待与放行。
3. 报告与控制台：模块的评估、出错条数不含跳过的条目，写明跳过了几条、为什么；任务成败小节不再把没有任务标注的条算成转人工。
4. 本机真 Daemon 跑一个带损坏样本的任务；推送后 CI 四项全绿；需求方过目。
