## 硬约束 · 现有 API 不动

本计划保持现有业务 API。**现有调用方无需修改代码、命令或配置**;唯一允许的
新增入口是下节明确列出的 enable/disable 测试开关,默认全部关闭。不开开关时走原路径。
业务源码已定位到 `backend/curation/`,实施前从实际代码和调用方固化接口基线;
下文历史行号仍需核对,尤其要区分 v1 `curation run` 与 v2 原子命令。

| 边界 | 必须保持 | 内部允许的改动 |
|---|---|---|
| Python API | 现有导出、函数/方法签名、参数默认值、同步/异步方式、返回类型与结构、异常约定 | 私有 helper、执行器、缓存与调度;`run_funnel` 不增加 `on_episode` 参数,不改成生成器 |
| CLI / 配置 | 既有命令、参数、配置键及默认含义不变;旧命令和旧配置直接可用 | 仅新增下节测试开关及其配置映射;不改变默认判定策略 |
| 结果 / 产物 | 现有 DataFrame schema、统计口径、JSON/CSV 字段及类型、文件名/目录约定、排序和去重语义 | 检查点与中间列留在内部;返回和导出前移除内部元数据 |
| VLM 调用边界 | 现有客户端工厂及 callable 签名、解析后的结果结构不变 | 请求内部合并、拆分与响应适配,但必须满足下述兼容门禁 |

**兼容门禁**:同输入、同配置、同一组固定 VLM 响应下,工程优化必须保留现有
`verdicts` / `per_episode` / `stats` 和 `checks`、`cam_votes`、`review` 等留痕字段
的存在性、类型与含义。不接受用空值或伪造票据补齐被省略的计算。对外有序的结果
按原输入顺序恢复,不能暴露流式完成顺序或改变 `duplicate_of`。

P2 / P5 / P9 中改变判定、提示词或留痕的方案先作为**内部实验**。质量 A/B 通过
不能替代 API 与默认行为兼容检查;无法保持既有契约的优化不进入本轮默认路径,
相应收益也不计入承诺。除下节测试开关外,不新增公开 API、配置项或产物格式。

## 测试开关 · enable / disable

### 入口与默认值

- 在 `curation run` 增加 `--enable <flag>` / `--disable <flag>`,可重复,每次一个名字。
  `--disable all` 显式选择原实现;不提供 `--enable all`,避免把实验混入基线。
- 配置统一放在 `pipeline.optimizations.<flag>: true/false`,复用现有深合并与
  `--set`。两种 CLI 写法映射到同一份配置,不增加 `run_pipeline` / `run_funnel`
  的形参;CLI 在调用前转换成既有 `set_overrides`。
- **全部 flag 默认 `false`**。缺省节点/键按关闭处理,旧配置文件无需补字段;
  `default.yaml` 注册已实现键,避免现有 `--set` 因中间路径不存在而失败。
- 优先级:出厂配置 < 站点配置 < `--set` < `--enable` / `--disable`。同名同时
  enable 和 disable、`--disable all` 同时带任意 enable 均报配置错误,不按参数顺序猜测。
- 未知名称、非布尔配置、尚未实现/不支持的开关、未满足的依赖在读取数据或调用
  VLM 前报配置错误。依赖必须显式开启,不能自动打开别的优化。
- flag 仅控制本次运行,不改环境变量或全局状态。日志记录请求值、实际采用路径与
  回退原因;v2 接入时沿用 stderr 事件,不改变 stdout JSON。Python 直接调用走
  既有配置入口,不开 flag 时行为不变。
- 下表是实施清单,**不是已实现能力**。先接入 v1 `curation run`;v2 的

### A/B 与恢复规则

以下为实现后的命令用法,其余输入、配置、episode 集合和并发参数保持一致。
各组使用独立输出目录,以免命中其他组的缓存或检查点。

```bash
# A: 原路径基线
curation run --input /data/droid --output /tmp/curation-ab/base --disable all

# B: 只测流式执行
curation run --input /data/droid --output /tmp/curation-ab/stream --enable streaming_funnel

# C: 流式 + 落盘,不复用旧结果
curation run --input /data/droid --output /tmp/curation-ab/checkpoint --enable streaming_funnel --enable checkpoint --disable resume

# D: 对 C 中断的运行恢复,必须匹配其输入/配置/实现/优化策略身份
curation run --input /data/droid --output /tmp/curation-ab/checkpoint --enable streaming_funnel --enable checkpoint --enable resume

# 已有 --set 的等价写法
curation run --input /data/droid --output /tmp/curation-ab/stream-set --set pipeline.optimizations.streaming_funnel=true
```

- `checkpoint=enable, resume=disable` 创建独立新运行,不删除或覆盖旧检查点。
  `resume=enable` 在已有交付目录内只选身份匹配的未完成运行;无匹配或有多个候选
  时明确报错,不猜测;沿用已有运行选择参数时仍须验证身份。
- 原始 flag 配置和归一化的执行策略都写入私有运行元数据。影响执行/结果的有效
  flag 值必须进入检查点指纹;`resume` 本身仅控制读取,从该指纹中排除,否则 C→D
  无法恢复。输入、模型、其他配置或实现版本变化仍使旧检查点失效。
- 测试至少覆盖全关、单项开启及必需依赖、逐项关闭、合法组合、冲突/非法值、
  失败后关闭回退、恢复身份隔离。关闭路径不得额外调 VLM 或触发新缓存/检查点 IO。
- A/B 对比旧返回值、留痕、排序、异常行为、VLM 次数/token、墙钟和峰值内存。
  工程组合通过后再跑 1000 条;质量实验单独回测,不自动晋升成默认开启。

## P1 · 结论即落盘 + 断点续跑

### 现状
`run_funnel` 内部列有五处 `collect()`(`funnel.py:399 / 419 / 646 / 917 / 954`),
verdict 在最后一次才算出来,所以最早能落盘的时刻是整批跑完。
崩一次 = 整批 VLM 开销归零。

顺带:`funnel.py:399` 是全量物化,10 万条会把所有 action/timestamps tensor 压在内存里。

### 改动

1. **保留 `run_funnel` 的现有签名与返回值,在内部拆出私有执行层**
   - `_build_funnel_chain` 只建惰性检查链,`_execute_funnel` 负责唯一一次消费
   - sink/回调只在私有执行层传递,不出现在公开参数或导出中
   - `run_funnel` 包装同一执行层,按原契约组装并返回结果;不得要求调用方消费 iterator
   - `run.py` 在已有输出上下文内接入检查点 sink;没有持久化上下文的旧调用仍按原行为返回
   - 硬门 drop 带内部标记到 sink 留痕,跳过后续解码/VLM

2. **把五个 `collect()` 换成一次 `iter_rows()` 流式消费**(见 P7 —— 这一条同时
   解决"即时落盘"和"真流水线",不要用分块驱动那种栅栏方案)
   ```
   # 私有执行层伪代码;公开 run_funnel 的参数和返回方式保持不变
   done = _load_done(checkpoint, run_identity)
   todo = _remaining_in_input_order(requested, done)
   df = _build_funnel_chain(read_lazy(..., episode_indices=todo), cfg, ...)
   for row in df.iter_rows(results_buffer_size="num_cpus"):
       _sink_internal_record(row)               # SQLite 事务提交
       _accumulate_legacy_result(row)           # 维护旧返回值/统计,不再执行惰性链
   ```
   `episode_indices` 管道已经是通的:`read_lazy` → `LeRobotDataSource.get_tasks`
   → `episode_select.reconcile_episodes`,resume 在内部计算 `requested - done`,
   不扩展 `read_lazy` 的公开签名。

3. **私有 SQLite 检查点**:完整保存重建旧返回值、统计和后续处理所需的字段,
   包括原始行序号;`run_id`、配置/输入/实现版本指纹、`kind`、`ts` 等放在内部封装中。
   从已有输出路径派生私有检查点位置,本地运行自动启用并恢复身份匹配的未完成批次,不改变正式产物 schema;
   正式 `per_episode` 不增加检查点元数据。

4. **pre-funnel caption 也要落盘**
   `run.py:702-720` 给无标注条目补 caption,**每条 1 次 VLM**。不落盘则 resume 整批重烧。
   同一张记录表以 `kind: "caption"` 区分。

5. 跑完由私有适配层合并历史记录与本次结果,恢复原顺序、完整 schema 与统计,
   再交给原有去重/画像/导出流程。不能仅保存简化版 verdict 就声称能重建旧结果。

### 纪律
- **幂等**:同一运行身份下按 `(kind, episode_id)` 取最后一条完整记录,caption 与判定不互相覆盖;配置、输入或实现版本变了不复用旧结果
- **恢复边界**:复用相同运行身份的未完成运行；SQLite 记录校验失败时明确报错
- **写盘**:每条记录提交 SQLite 事务,使用 `synchronous=FULL`
- **Ray**:多进程写入需单写者或分库合并,不共享单个连接

### 附带收益
流式执行减少中间全库物化,解码段与 VLM 段可以重叠(见 P7)。
若旧 API 要求返回全量 DataFrame/列表,仍保留最终结果所需内存;不能为了宣称
常量内存而更改返回类型。内存验收区分处理中间态与旧契约要求保留的结果。

## P2 · 合并 VLM 请求:4 次预算

**状态:内部实验目标,不作为本轮默认行为。** 4 次预算涉及早停、少复核机位和
提示词变化,不能仅凭最终 verdict 相同认定兼容。请求合并必须由私有适配层恢复
现有 callable 的返回结构;无法保留现有结果语义与留痕时继续使用旧请求路径。

### 立论
一个**单词**答案的请求延迟 22.8s,而 6 张 448 图的 prefill 撑死一两秒、5 个 token 的
decode 不到 0.1s —— **两者都解释不了 22.8s**。大头是推理 token(代码里有
`strip_reasoning` 剥 `<think>`)或服务端每请求固定开销。

两种情况下合并都赢:推理 token 占大头 → 8 个问题走一次推理而不是 8 次;
固定开销占大头 → 按请求数除。

⚠️ 这与 v2/v4 的失败**正交**:那两次死在**图片维度**(多张异时刻图,模型跟不住
哪张是哪张);这里是**问题维度**,图不变。

### 4 次预算

```
第 1 次   打分·末段    3 参考帧 + 末 2 个时刻 × N 机位,问 2 个分数
          └─ final = median(末2) >= 0.8 → 强成功候选,直接过   ★ 多数条目到此为止
第 2 次   打分·补探    其余 6 个时刻合并,拿 peak / voc / gap
第 3、4 次 复核        **两个机位各一次**(双问合并),两路并行 = 1 跳;整层可关
```

### 为什么第 4 次必须给"第二个复核机位",而不是别的

`tally`(`task_success.py:257`)只数实票:`0 yes 且 >=1 no → "no"`。
单机位复核时,这一路的 `no` 就直接构成 `tally == "no"`,撞上失败候选那一行
就是 `◆全表唯一杀格:双签` —— **一路证人即可判废**。

而这个仓库已经为"孤证杀"付过账:`task_success.py:489` 写着
"③ 杀需 >=2 条有效路:实测只有一路的杀 5 条全是冤杀"。
那是仲裁侧的教训,复核侧的结构一模一样。

所以 3 次预算(复核只剩 1 路)会把判废退回孤证状态。第 4 次买的不是精度,
是**判废资格**。两个机位并行发,墙钟上仍是 1 跳。

实验可以比较 **2** 个复核机位(主相机 + 次相机),DROID/Bridge 按名字序取前两路。
现有 `max_endstate_cams` 配置及默认值保持不变;减少机位会改变票据内容,
不能在默认路径中把用户配置的 4 路静默截断成 2 路。

### 为什么第 1 次就能定强成功候选

`parse_completion` 末行是 `np.clip(v, 0.0, 1.0)`,所以分数上界 1.0。于是:

```
final >= 0.8  ⟹  gap = peak - final <= 1.0 - 0.8 = 0.2
```

`task_success.py:206` 的 `strong = (final >= 0.8 and gap <= 0.2) or ...` 里,
**后半个条件恒真**。这一分支等价于 `final >= 0.8`,而 `final = median(preds[-2:])`
只依赖末两个探针。

再叠加决定表的事实:`init == "success_cand"` 且 `strong == True` 时,复核的
yes/no/split/abstain **四格全部只写留痕字段,不动 `passed` 也不动 `verdict`**
(`task_success.py:354-385`,实施前核对)。这至多说明最终判决可以等价,
**不说明完整 API 结果等价**:跳过复核会缺少 `cam_votes` / `review` 等留痕。
既有契约下仍须保留这些计算与字段,不能将这部分节省直接计入落地收益。

| 2.6 | 仲裁 judge 内部用 `n=3` | 3 发 → 1 发 | 先探端点支持,验证采样/票据语义;适配回原结果结构,不支持则回退原调用 |

### 2.5 的语义(不是"判废能力归零")
`task_success.py:317` 的 `cam_voter is None` 分支已经定义好了:失败候选
`passed=False → None`,而 `passed is None` 正是仲裁的触发条件(`funnel.py:843`),
仲裁自带双签(`kill_min_lines=2`)。等于把第二签名从复核换成仲裁。
代价:仲裁是**串行链**(出题→定位→判官,3-4 跳),复核是**全并发 1 跳**。
因此只在私有实验中评估,默认复核与仲裁触发规则保持现状。

### 内部实验的决定表
实验按 `{初判档: 是否需要第二签名}` 比较策略,由上节相应 flag 控制,
不新增业务函数参数,也不替换既有默认决定表:

| 初判档 | 复核的权力 | 实验策略 |
|---|---|---|
| 强成功候选 | 无(四格全留痕) | **关** |
| 弱成功候选 | 有否决权(`weak_success_vetoed_by_review`) | 开 |
| 失败候选 | 唯一杀格,且比仲裁便宜快 | 开 |
| 灰区 / gap / tripwire | yes 能救回(`review_rescue`) | 开 |

### P2.3 不过关时的退化路径
"多时刻合并"(第 2 次把 6 个时刻塞进一个请求)是 v4 翻车的地盘,A/B 不过就降级:

| 退化级别 | 第 2 次怎么发 | 总次数 |
|---|---|---|
| 目标 | 6 时刻合 1 次 | **4** |
| 降级一档 | 6 时刻拆 2 次(各 3 时刻) | 5 |
| 完全退回 | 逐时刻 6 次 | 9 |

这些请求数以其余实验策略成立为前提,不是保持当前 API 契约后的保底收益。
P2.3 不阻塞其余独立实验;每项是否进入默认路径都以兼容门禁为准。

## P3 · 打开线程池天花板(P2 的前置,不是现状的瓶颈)

### 先更正一件事

`funnel.py:882` 每条 episode 的同步工作走 `asyncio.to_thread(...)`,用的是
**事件循环的默认 executor** —— 全仓库没有任何地方配置过,即 CPython 默认:

```python
ThreadPoolExecutor(max_workers=min(32, os.cpu_count() + 4))
```

**关键:那个 `32` 是硬天花板,和核数无关。** 128 核机器上它也是 32。

生产机 32C ⇒ `min(32, 36) = 32`,**正好等于 `vlm_episode_concurrency: 32`**。
所以现状下它不是瓶颈 —— 两个限制刚好同值,看起来"配置生效了"。
(此前推断"8 核 → 12 卡住并发"在 32C 机器上不成立,作废。)

### 但它是 P2 的拦路虎

P2 合并请求之后,每条 episode 不再扇出 8 个并行请求,而是**串行发 1~2 个**。
于是 `在飞请求数 ≈ episode 并发`,要把在飞数维持在方舟已验证的 ~117,
`vlm_episode_concurrency` 必须从 32 提到 96 左右。

**而线程池天花板 32 会把它按死,且没有任何报错、没有任何日志。**
配置写 96,实跑 32,只是慢三倍。

### 改动

私有执行层持有专用 executor,把原 `to_thread` 的同步任务提交到该池:
```python
executor = ThreadPoolExecutor(max_workers=episode_concurrency + 8)
# 生命周期由私有执行层管理,在完成/失败/取消后统一回收
result = await asyncio.get_running_loop().run_in_executor(executor, work)
```
由已有 episode 并发配置推导大小,仅由 `dedicated_executor` 开关选择路径。迁移时保留 `to_thread` 的
contextvars 传播和原有异常/取消约定;库调用不能替换调用方共享的默认 executor,
也不能把同步 API 改成异步。

这些线程绝大部分时间阻塞在 `requests.post` 等方舟,不吃 CPU
(`funnel.py:858`:"绝大部分是等服务端响应,CPU 闲着"),
所以线程数可以远超核数 —— 32C 上开 128 个阻塞线程完全正常。

### 验证
```bash
CURATION_DEBUG_CONCURRENCY=1 ...   # funnel.py:880 探针会打 在飞=N 峰值=M
```
改配置到 96 后,峰值若仍停在 32,就是这个天花板。

### 现状有效并发 43 的解释
不是线程池卡的(32C 上它=32),而是:
三把请求闸门(probe 64 / endstate 64 / arbitration 32)+ 32 条 episode
彼此不同步(有的在解码、在算,此刻不发请求)。
`default.yaml:119` 的实测也印证:probe 闸门 64 只用到 67%。

### 顺带修一处错注释
`funnel.py:867` 写 "总并发 = vlm_episode_concurrency × vlm.max_concurrency,两层相乘"
—— probe 的闸门是工厂建一次、所有 episode 共用(`vlm_client.py:814`),
`default.yaml:13-15` 已明确纠正为"三类请求的在飞上限各自独立"。funnel 那条没跟着改。

## P4 · 非 VLM 段:三次全量解码 + 两次全量重读

判定段降到小时级之后,这些就不再是"3%"了。

### 4.1 同一批帧被解了三遍

| # | 在哪 | 参数 |
|---|---|---|
| 1 | 抽帧段 `frame_checks`(视觉质量 + 同步共用) | `sample_interval_s=interval, max_side=448` |
| 2 | VLM 判定段 `_task_check_sync`(`funnel.py:906`) | **完全相同的参数** |
| 3 | M7 caption `caption.py:_one` | 自己再解一遍 |

三次的参数一致,结果逐字节相同。现在这么写是因为 daft 列里塞不下解码帧
(3 路 × 40 帧 × 600KB ≈ 72MB/条)。

**改法**:由私有缓存层复用相同解码参数下的帧,现有抽帧/检查/caption API 不加参数。
key 包含输入身份、episode、机位和全部解码参数,按在途 episode/字节预算限制容量,
最后一个消费者结束后释放,与 P1/P7 的流式消费衔接。
默认使用无损缓存;JPEG q85 会改变像素与判定输入,只能作为独立质量实验,
不能宣称逐字节等价。若试 JPEG,448px 约 40KB/帧、约 5MB/条的容量估算需另测。

### 4.2 去重第一道的全量重读可以整个删掉

`run.py:839` 为了算 action 指纹,把全部 keep 行分批 200 **重新读一遍 parquet**。
但 `dedup.py:74` 的 `action_hash(row)` **只用 `row["action"]`** ——
而 `action` 本来就是 funnel DataFrame 的一列,数值段已经读过了。

**改法**:数值段内部计算 `_action_hash`(纯 CPU 的 daft UDF,零额外 IO),
随私有检查点交给去重阶段。移除 `run.py:839` 的重读循环,但复用原有指纹算法;
返回/导出前移除内部列,不扩展公开 DataFrame schema 或 `per_episode` 字段。

10 万条省一次全量 parquet 重读。

### 4.3 视频内容哈希的"不并发"可以拆开

`run.py:855` 注释:"**不并发** —— 谁是首见、谁被判重复取决于遍历顺序"。
但顺序只影响**裁定**,不影响**哈希计算本身**。

**改法**:并发算哈希 → 按原顺序串行裁定首见。`duplicate_of` 逐字节不变。
只影响撞车组,量小,但撞车组恰恰是要读视频字节的那批(最贵)。

### 4.4 光流是全管线最贵的 CPU 计算

`funnel.py:447` 原话:"N 路相机 ≈ N 倍光流,全管线最贵的 CPU 计算"。
P2 的内部实验会比较 2 路复核机位,同步检查是否也只需要前 2 路值得一议 ——
但这**动判定口径**(`video_action_sync` 的判废要"所有可信相机一致"),要回测。
先不动,列在这里备查。

## P6 · probe 走批量推理接口(可选)

复核/仲裁是链式依赖(要等上一层结论),请求内容跑之前不存在,没法预先打包。
**probe 不一样**:一条 episode 的探针互不依赖,全库所有 episode 的 probe
请求都能在跑之前一次性枚举。

两阶段:
```
阶段 A  全库枚举 probe 请求 → 批量接口提交 → 结果落 SQLite
阶段 B  读 SQLite 算打分层结论 → 只对需要的条目跑复核/仲裁(在线)
```

和 P1 的 SQLite 检查点是**同一套地基**,阶段 A 的产物天然就是可续跑的。
收益取决于方舟批量推理的实际折扣与配额(**待确认**);代价是延迟以小时计,
不适合"跑 10 条看一眼"的调试循环。先由 `batch_probe` 实验开关控制,默认关闭;
端点能力与超时/错误/返回契约未验证前,只在隔离测试中启用,不接入正式结果路径。

## P7 · 让它真的成为流水线 🔴 必修

### 现状:不是流水线,是逐段栅栏

`run_funnel` 里有五个 `collect()`(`funnel.py:399 / 419 / 646 / 917 / 954`),
每一个都是**硬同步点**:

```
数值段  全部 episode 跑完  ──┐
                            ├─ 栅栏
抽帧段(解码+光流,吃 CPU) 全部跑完 ──┐
                                      ├─ 栅栏
VLM 段(等方舟,CPU 全闲)  全部跑完 ──┘
```

抽帧段是 **CPU 密集**(`funnel.py:447`:"N 路相机 ≈ N 倍 Farneback 光流,
全管线最贵的 CPU 计算"),VLM 段是**纯网络等待**(`funnel.py:858`:
"绝大部分是等服务端响应,CPU 闲着")。两段用的是**完全不相交的资源**,
却被栅栏强制串行,一点不重叠。

### 这些 collect 是怎么来的

不是为了流水线,是为了修 2026-07-10 那个"懒重算 8 次"的 bug
(`funnel.py:397` 注释:"daft 惰性,每个 count_rows/to_pydict 都会从头重算整条检查链")。

根因是**驱动侧有多个终结动作**:`count_rows()`(统计)、`_capture_killed` 的
`to_pydict()`(捞被杀行留痕),每一个都触发一次完整重算。
加 `collect()` 是把重算钉住,代价是把流水线拍平。

daft 本身是 morsel 流式引擎(`iter_rows` 见 `dataframe.py:476`,
带 `results_buffer_size` 背压),**只要全链只有一个终结动作,每个 UDF 天然只跑一遍**,
morsel 1 可以已经在 VLM 段而 morsel 5 还在解码。

### 改动

把私有执行层的多个终结动作全部收进**一次** `iter_rows()`;
公开 `run_funnel` 仍返回既有对象,不能把 `iter_rows()` 或新 builder 暴露给调用方:

| 现在 | 改成 |
|---|---|
| `stats["input"] / after_numeric_gates / survivors_for_vlm` 用 `count_rows()` | sink 侧累加计数 |
| `_capture_killed` 用 `.filter().to_pydict()` 捞被杀行 | 带私有 `_killed_by` 标记列随流走;下游 UDF 见到标记直接早退 |
| `stats["arbitration"]` 扫 `to_pydict()` | sink 侧累加 |
| 终物化 `collect()` | 私有执行层 `iter_rows()` 边出边写检查点,包装层恢复旧返回值 |

⚠️ **硬门的短路语义必须保留**:被杀行不得执行后续解码/VLM。
统一使用标记随流到末端、sink 分流的方案,不在 UDF 内写盘;
包装层只向原返回集合放回原本应返回的行,被杀行按原留痕契约组装。
内部标记在返回/导出前移除,不能为了保留 drop 行而改变公开结果集合。

### 收益随 P2/P3 放大

| | 非 VLM | VLM | 串行合计 | 重叠后 | 省 |
|---|---|---|---|---|---|
| 现状 | 1.2s/条 | 9.2s/条 | 10.4 | 9.2 | 12%(不值得单做) |
| P2+P3 后(并发 96) | 1.2s/条 | 0.68s/条 | 1.88 | 1.2 | **36%** |

(非 VLM 的 1.2s/条 来自 `default.yaml:12` "10 条 DROID 关掉 VLM 仅 12s";
VLM 的 0.68s/条 来自时间测算那节的并发 96 场景。)

**也就是说:P2/P3 把 VLM 段砍掉之后,解码+光流会变成新的主要矛盾,
而它现在和 VLM 段完全不重叠。** 所以 P7 不是锦上添花,是 P2/P3 的必要配套。

### 🔴 回归护栏:必须防住"重算 8 次"悄悄回来

去掉 `collect()` 之后,**任何一个新加的驱动侧终结动作都会让整条懒链重跑一遍**,
而且不会报错、不会崩,只是悄悄贵 N 倍 —— 2026-07-10 那个 bug 就是这么活了一阵子的。

护栏两道:

1. **单元测试钉死"每个检查每条 episode 只调一次"**。
   现成的计数点就有:`funnel.py:224` 的注释已经指出"三个检查是三个独立 UDF,
   每条 episode 会过 3 次 → 只在最后一个启用的检查里 tick,否则计数变 3 倍"。
   用假 VLM + 计数器覆盖存活行、硬门 drop、禁用检查和 resume:
   每个应执行的检查每条恰好一次,短路/禁用/已恢复的检查为零,不能一律断言都等于 N。
2. **`_build_funnel_chain` 内禁止出现终结动作**。
   `collect` / `count_rows` / `to_pydict` / `show` 在该函数体内一律不许用;
   加一条 lint 或测试(AST 扫描)把这个纪律钉住,不靠人记。

没有这两道,P7 的收益随时会被下一个"我就统计一下"的改动吃光,而且**看不出来**。
此外必须通过接口契约回归:固定输入与假 VLM 响应,逐项比较旧入口的签名、返回类型、
schema、统计、留痕、结果顺序与异常行为;覆盖空输入、全 drop、中断恢复。

### 与 P1 的关系

**是同一个改动。** `collect()` → `iter_rows()` 一次给两样:
行一条条流出来 → 立刻提交 SQLite(P1);整条链恢复流式 → 解码与 VLM 重叠(P7)。
变化都在私有执行层内,调用方继续使用原入口和返回值。

所以 P1 不要写成"分块驱动 + 每块落盘"——那是把栅栏从五个减到 N 个,
resume 有了但流水线还是没有。

| `_HTTP_STATS` / `_LAT_ROWS` | `vlm_client.py:36/42` | 延迟与 token 记账散在各 worker | 每 worker 落一份 csv,收尾合并(`read_latency_csv` 已经存在) |

`_EPISODE_SEM`(`funnel.py:159`)同理:每 worker 一把 → episode 并发也是 worker × 本值。

### 配置上的连带

**总在飞 = worker 数 × 每 worker 闸门容量**,这是压在方舟配额上的唯一旋钮。
4 worker 想要总并发 96,每 worker 就该配 24,而不是照抄 96。
现有配置值的含义不能随 runner 改变。内部调度器应在保持原语义的前提下分配
worker 容量;若已有键表达的是每 worker 上限,不得静默解释成总上限。
若需要新增 worker/配额配置才能正确部署,移出本轮范围,先保留当前 runner。

## P9 · 关掉 thinking 🔴 可能是最大的单项

### 立论

一个**单词**答案("yes"/"no"/一个整数)的请求,均延迟 **22.8s**,零排队。
输入 ~2,500 token、输出 ~5 token,两头都解释不了 22.8s。
唯一合理的解释:**模型在输出答案之前想了几百到上千个 token。**

佐证:
- 五处 payload 构造(`vlm_client.py:678/817/919/1075/1198`)**没有一处传 thinking 参数**
- `max_tokens: 2048` 给足了思维链空间
- `strip_reasoning`(`vlm_client.py:584`)专门剥 `<think>…</think>` —— 这条链路确实见过大段推理

而这些题是**单轮看图答一个词**,不是多步推理。thinking 大概率是纯开销。

### 改法:分类型 enable / disable 开关

```python
def _thinking_for(kind: str, experiment_policy): ...  # 仅私有实验层
```
统一用 `pipeline.optimizations.thinking_off_<kind>` 和对应的 enable/disable
入口,不另建 `checks.task_success.vlm.thinking.<kind>` 这套重复配置,不改变现有
客户端工厂或 callable 签名。flag 默认关闭,沿用当前请求参数;enable 时由私有
策略层在确认端点支持后才发送关闭 thinking 的字段。disable 恢复原请求,
不强制打开 thinking。保留原有解析与异常约定。

**必须分类型,不能一刀切:**

| 调用类型 | 题目性质 | 预期 |
|---|---|---|
| probe / endstate / judge | 看图答一个词 | **关**(收益最大) |
| grounder | 看图给坐标框 | 关(待测) |
| question_writer | 把意图拆成取证题 | **留**(真推理) |
| M7 的 4 个文本 LLM 步骤 | 体系归纳/合并/分配 | **留**(输入长、真推理) |

### 测试要两个轴,缺一不可

**速度轴**:延迟、`completion_tokens`、实际 TPM(依赖阶段 0 的 usage 记账)
**质量轴**:105 条人工真值 + droid-200,冤杀率不得上升;
probe 还要看 VOC 与分数分布有没有漂移(打分是连续量,比 yes/no 更敏感)

⚠️ **这是判定质量改动,不是纯工程优化。** A/B 只用于评估收益;
本轮默认路径保持现有判定策略,不能因质量轴通过就静默关闭 thinking。

### 如果延迟真的从 22.8s 掉到 ~3s

下面保留的是 **TPM 提至 5M 且 RPM 同步提高**时的旧假设,不适用当前
RPM 500 / TPM 1M 配额,也不代表本轮默认路径会关闭 thinking。

| | 每条墙钟 | 需要并发 | 10 万条 | TPM |
|---|---|---|---|---|
| thinking 开(现方案) | 2.6 跳 × 25s = 65s | **~550** | 3.3h(顶配额) | 5M |
| thinking 关 | 2.6 跳 × 3s = **7.8s** | **~90** | **~2.5h(顶配额)** | 5M |

两件事同时发生:
1. **墙钟下限从 3.3h 降到 ~2.5h**(输出 token 变少,同样 5M TPM 能过更多条)
2. **需要的并发从 550 降到 ~90** —— 可用 P3 的私有线程池承接,不必为 VLM 并发引入 Ray

第 2 条比第 1 条重要得多:550 并发要拆进程、要处理跨进程的闸门与记账;
90 并发是单进程一行配置的事。

### 排期

放进**阶段 0 的内部实验**,和 usage 记账一起评估收益。它不作为默认路径修改,
也不是 P1/P7 工程改造的前置;实验结果用于评估后续方案。

## 时间测算

**以下包含原方案的条件估算,不是本轮 API 不变方案的验收承诺。**
4 次请求预算、关闭 thinking、减少机位和 caption 合并均涉及尚未通过门禁的实验。
默认路径保留这些行为时,必须用 P1/P3/P4/P7 落地后的实测重新估算总时长,
不能直接承诺 12~34 小时或按 thinking 已关闭来调整默认并发。

### 逐段吞吐

| 段 | 现状 | 实验目标成立时 | 依据 |
|---|---|---|---|
| VLM 判定 | 9.2s/条(有效并发 43) | 65s/条 ÷ episode 并发 | 50 条/7.7min 实测;P2 后 2.6 跳 × 25s |
| 非 VLM(数值+解码+光流) | **1.2s/条** | 1.2s/条(P4 后略降) | `default.yaml:12` "10 条关掉 VLM 仅 12s" |
| M7 caption | ~1 次 VLM/keep 条 | ~0(P5 搭车) | `run.py:288` |
| 去重第一道 | 全量重读 parquet | 0(P4.2 算成列) | `run.py:839` |
| 交付导出 | **未测** | **未测** | `run.py:1409` 起 |

### 配额才是天花板(RPM 500 / TPM 1,000,000)

两条限额的**平衡点是每请求 2,000 token**(1,000,000 ÷ 500)。
我们现在每请求约 2,500~2,800 token ⇒ **略偏 TPM 先顶住**,但两条挨得很近,
优化一条就会立刻撞上另一条。

按 Little's law,跑满 RPM 500 所需的在飞请求数 = `8.33 req/s × 单次延迟`:

| 单次延迟 | 跑满 RPM 500 需要在飞 |
|---|---|
| 22.8s(thinking 开) | 190 |
| 3s(thinking 关,待测) | **25** |

现状在飞 43 ⇒ 实际只用到 **113 RPM(23%)**。

### 10 万条:VLM 侧

| 场景 | 请求/条 | token/条 | RPM 下限 | TPM 下限 | **取大者** |
|---|---|---|---|---|---|
| 现状 | 17.4 | 46,000 | 58h | 77h | **77h(3.2 天)** |
| 现状实跑(并发 43) | — | — | — | — | 12.6 天(我方受限) |
| + P2 | 3.5 | 9,900 | 11.7h | 16.5h | **16.5h** |
| + P2 + P9(thinking 关) | 3.5 | 7,500 | 11.7h | 12.5h | **12.5h** |
| + 再降 token(前缀缓存/降图) | 3.5 | ≤5,500 | **11.7h** | 9.2h | **11.7h(RPM 硬墙)** |

**假设平均 3.5 请求/条,VLM 侧下限约 11.7 小时,受 RPM 500 限制。** 再往下只有两条路:
提配额,或走批量推理接口(P6,通常独立配额)。

### 若 thinking 实验成立,并发需求的条件变化

thinking 关掉后只需要**在飞 25**(episode 并发 ~21)就能跑满 RPM 500 ——
**比现在配置的 32 还低**。

| 项 | 原定位 | 配额已知后 |
|---|---|---|
| P3 打开线程池天花板 | 🔴 头号 | 若 thinking 关闭,96/550 并发用不上;当前默认路径仍按实测评估私有线程池容量 |
| P8 Ray 多 worker | 条件性 | **VLM 侧取消**(共用同一份配额,多 worker 不增加吞吐);仅当 CPU 侧扛不住才需要 |
| P6 批量推理接口 | 可选 | **升级**:唯一能绕开 RPM 500 的路 |
| P2 减请求/减 token | 核心 | **仍是核心**(RPM 和 TPM 都按比例降) |
| P9 关 thinking | 🔴 最大单项 | **仍是**(16.5h → 12.5h),但不再改变并发结构 |
| P7 拆栅栏 | 🔴 必修 | **更重要了**(见下) |

### 实验目标达成后可能出现的新瓶颈:非 VLM 段

VLM 侧压到 ~12h 之后,非 VLM 段(数值+解码+光流)按 `default.yaml:12` 的
0.83 条/s 外推 = **33.6 小时**,**反超 VLM 段近 3 倍**。

- 没有 P7:总时长 = 12h + 33.6h = **45.6h**(栅栏串行相加)
- 有 P7:总时长 = `max(12h, 33.6h)` = **33.6h**,瓶颈整体翻到 CPU 侧

所以 P7 从"锦上添花"变成"决定性的";而 CPU 侧能不能从 0.83 条/s 提上来
(32C、以及 P4 去掉两次重复解码之后),成了整个计划最大的未知数。
**如果 CPU 侧也提不上去,P8/Ray 会因为 CPU 而不是 VLM 重新变成必需。**

### 结论

| | |
|---|---|
| VLM 侧硬底 | **~11.7 小时**(RPM 500 封死) |
| 非 VLM 侧(未测,按 0.83 条/s 外推) | ~33.6 小时 |
| **实验目标成立时的总时长** | **取决于 CPU 侧能提到多少,乐观 ~12h,悲观 ~34h** |
| 现状 | ~12.6 天 |

**1000 条完整跑批是工程路径的关键验证**:测出保持当前 API 与默认判定策略时
的 CPU/VLM 吞吐、最终结果内存及端到端耗时,再决定 P8 是否必要。
12~34 小时仍只是上述实验假设全部成立时的估算。
