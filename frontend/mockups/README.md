## 手动验证步骤

```bash
# 在仓库根目录起一个静态服务（页面之间有跳转，用 http 打开体验完整）
python3 -m http.server 4173 --directory frontend/mockups
```

浏览器打开 <http://localhost:4173/tasks.html>，按下面逐页对照。按钮不接后端，点了之后顶部会出一条小提示，说明真实页面会做什么。
右下角的黑色浮标是预览稿标记，点一下可关闭。

### 贯穿三页的同一个任务

详情、报告、裁决三页讲的都是「droid 前 50 条质检」，数字处处一致：

- 输入 50 = 通过 41 + 拒绝 7 + 待补跑 2，通过率 82%。通过里含待裁决 10 条（已裁 3 条、待裁 7 条）。
- 拒绝 7 = 任务成败判定 5（ep 6、11、23、38、45）+ 时间戳检查的残段 1（ep 18）+ 精确去重 1（ep 44）。
- 待补跑 2：ep 7、ep 31，任务成败判定的取证仲裁请求超时，主流程和重试都没过去。
- 经过：主流程跑到 VLM 档时 Daemon 升级、系统暂停又自动恢复 → 主流程结束时技能画像整体失败，结果版本 r0001 是「通过 0 · 待补跑 43」、没有导出 → 重试 #1 补齐技能画像，得到当前版本 r0002 → 交付数据集待导出。
- Token：输入 2.01M · 输出 67.5K · 思维链 42.9K · 缓存命中 931.8K · 请求 886 次（主流程 794 + 重试 92）。
- 数据集是 droid_100（LeRobot v3，robot_type 为 unknown），所以运动学极限没有跑，用来演示报告里「未运行」的模块。

### 1. 任务列表 `tasks.html`

1. 第 1 页摆出九种状态：待启动（蓝框）、排队中、运行中（蓝，呼吸点）、部分错误（橙）、已完成（绿）、已暂停 · 系统将自动恢复（灰，带循环图标）、已暂停、失败（红）、已停止。
2. 「so101 夜间批次」补跑成功后显示「已完成」；名称旁的「补跑过 1 次」悬停可以看到经过。
3. 「droid 前 50 条质检」：部分错误 +「待裁决 10」+「交付待导出」；点名称进任务详情，点「待裁决 10」进人工裁决。
4. 每行「更多」里的操作随状态变：待启动给编辑 / 复制为新任务 / 删除；排队中给取消排队；运行中给暂停 / 停止；系统暂停的「恢复」置灰；终态给查看报告 / 复制为新任务 / 清理交付产物 / 删除。未结束的任务，「删除」置灰并说明原因。
5. 「删除」和「清理交付产物」是两个动作：删除只删平台记录，30 天内可恢复；清理交付产物的弹窗列出完整路径和体积，输入任务名称后「清理」按钮才能点。
6. 底部页码分页：共 128 条；点页码翻页（第 2 页起是生成的历史任务）；每页条数切 10 / 20 / 50 / 100，页数跟着变；「前往」输入页码回车跳转。
7. 状态筛选里有「已删除（30 天内可恢复）」。

### 2. 新建任务 `task-new.html`

1. 必填项都有红色 `*`。清空「任务名称」，点「保存为待启动」或「创建并开始」：输入框标红，下方出现错误文案。
2. 基本信息多了「备注」（选填）。数据来源切到「HuggingFace 缓存桶」：只剩数据集下拉，地域置灰，访问密钥显示「不需要（匿名只读）」。
3. 交付目录有自己的地域和访问密钥：示例里数据集用只读的 readonly-tos，交付用 prod-tos，写探针已通过。
4. 预检结果三条：识别成功（绿）、88 条没有任务标注（蓝）、未读到机器人型号（黄）。
5. Episode 选择三种：全部 / 前 N 条 / 自选。切到「前 N 条」默认 50，右上角变成「已选 50 / 200 条」，填 0 或 300 会标红；自选的格子显示 ep 0、ep 1……
6. 质检范围预设：「完整质检」开 6 个模块；「快速质检」只开 4 个，「模型配置」整块隐藏，底部的检查项少了「模型能调通」；手动改任一勾选，预设自动切到「自选」。
7. 运动学极限：选一个机器人型号，卡片变成正常的勾选态并计入模块数；点「跳过该模块」恢复警告态，注明已跳过。
8. 模型配置：「VLM 后端」「模型」必填；思考强度默认「模型默认」，选 high 会提示放宽超时。
9. 展开「高级设置」：说明这里只能设上限；有模型调用重试次数上限、超时对冲、CPU 并发上限、VLM 并行度上限（留空为不限）、五类调用超时、导出交付数据集、预生成裁决片段。
10. 底部操作条吸底：「保存为待启动」「创建并开始」，左边写着开始前要过的检查。

### 3. 任务详情 `task-detail.html`

1. 页头：部分错误 + 待裁决 10 + 交付待导出；按钮是 重试（2 条）/ 人工裁决（10）/ 查看详细报告 / 更多（重新导出、复制为新任务、清理交付产物、删除）。「改名称和备注」弹窗只能改这两项，名称必填。
2. 虚线框里的「预览稿」开关切到运行中 / 已暂停 · 系统将自动恢复 / 已暂停 / 待启动 / 已完成 / 已停止：页头按钮、状态说明和分档进度跟着变。运行中能看到「预计还要 5 分钟」；系统暂停时「恢复」置灰。
3. 置顶横幅「判决已更新，交付数据集待重新导出」+「重新导出」按钮（弹窗说明 v3 源要重编码受影响的分块、导出后逐文件核验）。
4. 报告概览六个数：总数 50 / 通过 41 / 拒绝 7 / 待补跑 2 / 待裁决 10 / 通过率 82%，旁边是「查看详细报告」。
5. 分档进度五根条：补任务描述 22/22、数值档 50/50、帧档 49/49、VLM 档 49/49（末尾橙色一段是 2 条出错）、判决之后 42/42；每根有耗时；下面一句话解释为什么 50/50 之后是 49/49。
6. Token 卡片：输入 / 输出 / 思维链 / 缓存命中 / 请求数，没有金额；明细在「按模块」「按子任务」之间切换。
7. 模块表：任务成败判定是「部分错误」，点「2 条待补跑」展开 ep 7、ep 31 的出错原因；「重试」弹窗说明只补跑这 2 条。运动学极限显示「未运行」和原因。
8. 执行时间线：创建 → 系统暂停 → 自动恢复 → 主流程结束（r0001，带「查看 r0001 报告」）→ 重试 #1 → 重试结束（r0002，当前版本，带「查看 r0002 报告」）。
9. 「更多信息」默认折叠，展开是任务配置和只读的执行计划（各档并发、闸门、N 怎么取）。
10. 「日志」页签：按档、按主流程 / 子任务、按级别筛选；「跟随最新」开关；顶部「加载更早的 N 行」演示往上翻懒加载。

### 4. 质检报告 `task-report.html`

1. 质检总览：50 = 7 + 41 + 2；判废原因分布三根条；待补跑的 2 条和「重试这 2 条」。鼠标移到图上的条形看数值。
2. 数据包完整性；本次质检范围按报告顺序列出 7 个模块，点名称跳到对应小节，运动学极限标「未运行」并写明原因。
3. 七个模块小节，顺序和范围表一致：
   - 运动质量：卡顿动作时间线，红 = 卡顿、橙 = 空闲、绿 = 正常；可切「只看卡顿 / 只看空闲 / 全部条目」和「卡顿时长（长的在前）」；鼠标移到色段上看起止秒数。
   - 视觉质量：三路相机各一张分数分布图。
   - 视频-动作同步：全库逐相机概览表；同步曲线卡片（每路相机的画面动量 / 关节速度曲线，右侧互相关曲线和 ±0.25 秒绿带，逐相机诊断）；切「只看有标注或异常的」，ep 3 那张消失。
   - 任务成败判定：弃权原因分布；判决卡按 打分层 → 复核汇票 → 护栏 → 仲裁 → 结论 排开，没走到的层是虚线；右上角「去裁决（6）」。
   - 精确去重：一组重复，ep 43 保留、ep 44 剔除。
   - 技能画像：注明结果来自重试 #1；技能分布条形图（点族名展开子技能，带「样本偏少」标记）、标注分歧 5 条、两级技能体系表；右上角「去裁决（5）」。
4. 明细表：四张表可切换，排序只能选下拉里的字段；「视觉质量 · 逐相机」147 行分两页，每页 100 行，用上一页 / 下一页翻。
5. 点任何 ep 编号，右侧抽屉打开这一条的判决卡、三路视频（「同时播放」三条进度一起走）、证据帧和各模块读数。地址带 `?ep=29` 可以直接打开这条。
6. 结果版本下拉切到 r0001，或从详情页时间线点「查看 r0001 报告」（地址带 `?rev=1`）：顶部出现历史版本横幅；总览变成 50 = 7 + 0 + 43；技能画像小节变成失败样式（错误信息 +「重试此模块」，历史版本里按钮置灰）。
7. 「性能剖析」页签（地址加 `#perf` 直接打开）：模型服务与容器配额；六个关键数；五类调用的延迟表（P50 / P90 / P99 + 分布小图）；各阶段墙钟占比；重试与合并；按调用种类的 Token。顶部在「全部 / 仅主流程 / 子任务 · 重试 #1」之间切换，所有数字跟着变。

### 5. 人工裁决 `task-adjudication.html`

1. 顶部说明裁决只属于这个任务。吸顶栏写着「已裁 3 条 · 待裁 7 条 · 3 条尚未应用」和「执行裁决」。
2. 按来源模块分组：「技能画像 · 标注分歧」5 条在前，「任务成败判定 · 证据不足，弃权」6 条在后。ep 29 两个问题在同一张卡片里，第二组开头有一行说明。
3. 每张卡片有三路视频和「同时播放」。标注分歧四个选项：采纳新标注 / 维持原标注 / 拿不准 / 自行改写标注（展开必填的输入框）；成败弃权三个选项：判成功 / 判失败 / 拿不准；卡片底部「其它原因，整条弃用」。
4. 在 ep 29 点「采纳新标注」，第 ② 问改成按新标注提问；再点「判失败」，计数变成「已裁 4 条 · 待裁 6 条 · 4 条尚未应用」。
5. ep 16 选的是「拿不准」：卡片标橙，仍算待裁。
6. 点「其它原因，整条弃用」：成败问题的按钮置灰并说明原因；再点一次撤销。
7. ep 4 已采纳新标注：下面多出选填的「顺手给成败结论」；留空的话，执行时按新标注重跑任务成败判定。
8. 「问题类型」「状态」两个筛选；从报告页「去裁决（6）」进来（`?source=task_success`）会自动筛到任务成败弃权。
9. 「执行裁决」弹窗逐条列出会执行什么、哪几条要重跑模型；确认后「尚未应用」归零，按钮变灰。
10. 「任务失败复议」页签：只列任务成败判定拒掉的 5 条；折叠说明里写明 ep 18、ep 44 为什么不在这里；「看视频」打开抽屉；选「恢复为可用 / 维持拒绝」计入尚未应用。

### 6. 密钥与资源管理 `credentials.html`

1. 从侧栏「密钥与资源」进入，两个页签：TOS 访问密钥（4）、VLM 后端（3）。
2. 访问密钥列表只显示名称、地域、验证状态和引用情况，不显示任何密钥内容。验证状态三种：已验证 / 未验证（附原因）/ 验证失败（附原因）。页签顶部说明保存时只验身份，读写权限在建任务、开始任务时检查。
3. 「新建访问密钥」：名称、地域、Access Key ID、Secret Access Key 都有红 `*`；空着点保存逐项标红；测试用存储桶选填。
4. 「编辑」：名称不能改；两个密钥字段没有红 `*`，占位写「已保存，留空表示不修改」；底部显示当前验证状态。
5. 删除 prod-tos：提示它正被运行中的任务使用，不能删。删除 old-ci：说明历史任务的报告和视频会读不了，需要重新绑定。
6. VLM 后端：编辑 ark-prod 看拉到的模型（勾选、思考强度只列有效档、并行度默认 64）；编辑 ark-ep 看拉取失败后的手填（Model ID 或推理接入点 ID，思考强度列全部 7 档）；编辑 vllm-a100 看自定义端点（思考强度默认不传）。「添加 VLM 后端」时方舟必须填 API Key，切到「自定义」变成选填。
7. 新建任务页「访问密钥」「VLM 后端」旁的「管理」分别跳到这两个页签（`credentials.html#vlm`）。

## 设计口径

颜色与尺寸全部取 Arco Design 的设计 token（火山控制台同源）：主色 `#165DFF`、
成功 `#00B42A`、警告 `#FF7D00`、危险 `#F53F3F`，中性色 `#1D2129 / #4E5969 / #86909C / #C9CDD4`，
边框 `#E5E6EB`，页面底色 `#F7F8FA`；顶栏 60px、侧栏 208px、按钮与输入框 32px、表格行 48px、圆角 2–4px。

图表：只有一个系列时统一用主色 `#165DFF`；需要区分几路相机、或画面和动作两条线时，依次用
`#165DFF / #0DA5AA / #E8590C`，这三色按色觉障碍模拟校验过区分度，和白底的对比度都在 3:1 以上。
状态色只表示状态；卡顿时间线的红 / 橙 / 绿沿用 v1 的三态含义，旁边有图例。线宽 2px，条形不超过 24px 粗，网格线是细实线；
鼠标移到图形上显示数值。

⚠️ 这份手写 CSS 只为预览存在，**不会进 React 工程**。正式开发用 `@arco-design/web-react` 组件库，
届时这里的 token 是对照表，不是代码来源。六页各自内联同一份样式：第一批的 token 块原样保留，
第二批新增的组件（页签、抽屉、弹窗、分页、时间线、图表等）放在紧跟其后的第二个样式块里。改样式记得六处同步。

## 已知的刻意取舍

- 数据全是假数据，任何按钮都不发请求，操作结果用顶部小提示代替。
- 未做响应式：控制台类产品以 1440px 及以上为主。
- 与火山控制台的像素级对齐留到后期整合（需求方已确认不急）。
- 列表页为了把各种状态放进同一页，「运行中」和「已暂停 · 系统将自动恢复」同时出现了。实际默认同时只跑 1 个任务，系统暂停只在升级那一两分钟里存在（见待确认 5）。
- 列表里所有任务都链到同一个详情页（droid 前 50 条质检）。
- 详情页的状态开关只切页头、按钮和分档进度，其余卡片保持「部分错误」时的内容。
- 模块整体失败的报告小节只在历史版本 r0001 里看得到：按规则，模块整体失败时所有条目都待补跑，放进当前版本数字就对不上了。
- 视频和证据帧是占位块，真实页面用 TOS 预签名地址直连。同步曲线只画了 4 张卡片。
- 明细表、日志和历史任务的行由页面脚本按固定规则生成，只为演示分页和筛选。

## 待确认（评审时请重点看）

1. 顶栏 / 侧栏的信息架构：目前只有「质检任务」「密钥与资源」两个入口，是否还需要「数据集」或「概览」。
2. 任务列表是否需要展示「质检模块」列，还是收进详情页。
3. 新建任务页是否要拆成分步（Steps）向导——目前是单页长表单。
4. 任务状态的中文叫法：「部分错误」/「已停止」/「已暂停」是否符合火山的术语习惯。
5. 系统暂停的显示：新 Pod 起来就自动恢复入队，所以「已暂停 · 系统将自动恢复」在列表里通常只存在一两分钟。列表还要不要这个标签，还是只在详情页的时间线里记一笔？
6. 日志的语言：日志原文来自命令行，按 02 篇 CLI 默认输出英文，稿子里原样显示。要不要翻译，或者至少把系统事件（暂停、恢复、子任务）写成中文？
7. 裁决页的分组：「按来源模块分组」和「一条 episode 一张卡片」同时成立时，两个问题都有的 episode 只放在第一个组里，第二组给一行说明。v1 在 2026-08-16 改成了只按 episode 合并、不分组。用哪种？
8. 复议的按钮叫法：v1 界面用「恢复为可用 / 维持拒绝」（2026-08-16 定，不用「捞回」），06 篇 §5.1 写的是「捞回 / 维持拒绝」。稿子用了 v1 的叫法，06 篇要不要跟着改？
