# Quality-Aware Behavior Driven Robotics Dataset Curation

Physical AI data curation and deduplication, evaluated on
[`lerobot/aloha_static_coffee`](https://huggingface.co/datasets/lerobot/aloha_static_coffee)
using the NVIDIA Cosmos Curator pipeline.

## Executive summary

Video-only deduplication — Cosmos Embed1's current approach — operates purely in
**perceptual space**. It answers the question *"do these two clips look the
same?"* But for robot learning, the right question is *"do these two trajectories
represent the same **behavior**?"*

> Cosmos Embed1 is excellent for visual deduplication.
>
> Robotics datasets require an additional state-action fusion layer to preserve
> behaviorally distinct demonstrations.

More importantly, it is not just detecting **what counts as a duplicate** that
matters — **resolving which duplicate to keep** is equally important. The DemInf
research paper proposes quality scoring and filtering as the way to make that
second decision.

This directory contains two independent tracks, one for each problem.

## Contents

| Script | Track | Purpose |
| --- | --- | --- |
| `episode_level_extract.py` | A | Extract episodes from the LeRobot dataset into per-episode `.pt` files. |
| `compare_embed1_vs_state_action.py` | A | Compare Embed1 video similarity against state/action similarity. |
| `compare_embed1_state_action_fused.py` | A | Add a third, fused trajectory similarity space. |
| `deminf_lerobot.py` | B | Score and filter episodes by state-action mutual information. |

**Track A** answers *what is a duplicate*. **Track B** answers *which duplicate to
keep*. Track B is fully standalone and shares no code or data with Track A.

## Environments

Due to dependency issues we ended up creating two distinct environments, one for
HuggingFace/LeRobot (**`curator`**) and one for Cosmos Embed1
(**`curator_embed1_test`**).

Cosmos-Embed1-224p uses `trust_remote_code=True`, which downloads model
implementation files into the HuggingFace cache. The cached `modeling_qformer.py`
imports a function from a location that differs across Transformers versions, and
this conflicts with the version LeRobot requires. Extraction and embedding
therefore cannot share an interpreter. The `.pt` file is the handoff format
between the two.

Track B has no such split and needs only `numpy`, `scipy`, `scikit-learn`, and
`pandas`.

See the [appendix](#appendix-cosmos-curator-install) for full setup.

## Track A — What counts as a duplicate?

### Stage 1: Extract episodes from the LeRobot dataset

Using the first environment, extract a few episodes from the LeRobot dataset in
`.pt` format. These are fed to the subsequent Embed1 environment for determining
similarity across them.

```bash
micromamba run -n curator python episode_level_extract.py
```

Writes `episodes_full/episode_*.pt`, each holding the full video, state and
action trajectories, plus metadata. Defaults to `MAX_EPISODES = 5` and stores
video as float16, since full-resolution episode video is large.

### Stage 2: Similarity check using the Embed1 model

```bash
micromamba run -n curator_embed1_test python compare_embed1_vs_state_action.py
```

The embedding is derived from the **entire episode**, not a single excerpt:

```text
Episode
    ↓
1100 frames
    ↓
8-frame window #1
8-frame window #2
8-frame window #3
...
    ↓
Embed each window
    ↓
Average (or max-pool)
    ↓
Episode embedding
```

**We did not use Embed1 for the state/action similarity check.** The script runs
two completely separate paths:

```text
Path 1:
video → Embed1 → video embedding

Path 2:
state/action → handcrafted vector → cosine similarity
```

So the comparison is between Embed1 visual similarity, computed by NVIDIA Embed1
from video, and state/action similarity, computed by our handcrafted feature from
raw state/action. The state/action comparison is done by **our own Python code**,
not by NVIDIA Embed1.

This is a constraint of the model, not a design preference. The Embed1 interface
strictly takes video or text as input, with no provision for accepting
state/action information. Per the
[model card](https://huggingface.co/nvidia/Cosmos-Embed1-224p):

> **Cosmos-Embed1: A joint video-text embedder for physical AI**
>
> **Input Type(s):** Text+Video
> **Input Format(s):** Text — UTF-8 string. Video — tensor scaled from 0 to 1 of
> RGB frame sequences.
> **Input Parameters:** Text — one-dimensional (1D). Video — three-dimensional (3D).

The public interface is essentially:

```text
video              text
  ↓                 ↓
Embed1            Embed1
  ↓                 ↓
256-d embedding   256-d embedding
```

We found no API like:

```python
processor(
    videos=video,
    states=state,
    actions=action,
)
```

So the embeddings generated by the Embed1 model are strictly for **video**
information only.

### Stage 3: Fused trajectory embedding

```bash
micromamba run -n curator_embed1_test python compare_embed1_state_action_fused.py
```

In this experiment we add a third similarity space: a fused embedding made by
concatenating normalized Embed1 video embeddings with normalized state-action
features.

In the last experiment, Embed1 only saw `video`, and the state/action similarity
was computed by our separate code. So the experiment was:

```text
Embed1(video)  vs  our_similarity(state + action)
```

What we now build is a **fused trajectory embedding**:

```text
video
            ↓
         Embed1
            ↓
     video embedding
            ↓
            ├────┐
                 │
state + action   │
      ↓          │
 behavioral      │
 embedding       │
      ↓          │
      └──────────┘
            ↓
      fused embedding
```

```python
fused_embedding = normalize([
    alpha * embed1_video_embedding,
    beta  * state_action_embedding,
])
```

`alpha` and `beta` are the `VIDEO_WEIGHT` and `STATE_ACTION_WEIGHT` constants.
This lets us compare Embed1-only similarity, state/action-only similarity, and
fused trajectory similarity side by side.

This stage also extends the state/action feature with **temporal deltas** beside
the absolute values, so it captures motion rather than pose alone.

## Track B — Which duplicate to keep?

`deminf_lerobot.py` implements
[arXiv:2502.08623](https://arxiv.org/abs/2502.08623), *Robot Data Curation with
Mutual Information Estimators*.

```bash
python deminf_lerobot.py
```

Requires no LeRobot import — it reads the parquet files HuggingFace has already
cached on disk, falling back to the `datasets` library if none are found. Set
`HF_HOME` if your cache lives elsewhere.

### The research paper

Data quality is critical to the performance of imitation learning algorithms, yet
little work has sought to measure it, and unfortunately techniques used for data
curation in vision and language do not transfer well to robotics. Pre-trained
models have been used to curate vision datasets but are incapable of reasoning
about actions. In contrast, the authors believe metrics for imitation learning
should be able to measure the relative predictability of the state-action
distribution directly, which affects how well a policy is able to fit the expert.
This work specifically explores how mutual information (MI) between states and
actions can measure demonstration quality.

To address this problem, the paper introduces Demonstration Information
Estimation, or **DemInf**. DemInf first learns a structured low-dimensional
representation of the state and action space using variational autoencoders. It
then leverages mutual information estimators based on k-nearest neighbors to
estimate the quality of state and action chunk pairs. Finally, it averages mutual
information estimates across time to identify the highest and lowest quality
demonstrations.

At its core, **DemInf is an automated quality labeling system**. Traditionally the
way you would identify good versus bad robot demonstrations is to have a human
expert watch every episode and rate it. This is expensive. DemInf replaces that
with an **unsupervised quality signal** — the MI score is essentially an automated
label saying *"this demo is worth learning from"*, without any human in the loop.

The insight is that **mutual information between states and actions** is the
right quality metric:

- **High MI** — diverse actions (the robot does different things in different
  states) and predictable given context → *good demo*
- **Low MI** — noisy or random actions, or actions ignoring the state → *bad demo*

The pipeline has three steps:

1. **VAE embedding** — encode high-dimensional states/images and action chunks
   into compact latent vectors, which makes kNN meaningful
2. **KSG estimator** — a k-nearest-neighbor based MI estimator that works with
   only 50–300 demos, unlike InfoNCE which needs millions
3. **Score & filter** — rank each trajectory by its average MI contribution and
   keep the top κ%

### Implementation

The code for the DemInf paper was not available at the time of writing, so this
is a reimplementation from the paper description. Key details follow.

**Embedding.** Squash high-dimensional observations into a compact space where
distances are meaningful. The paper uses VAEs; we use PCA with z-scoring instead.

*Why PCA instead of VAE.* PCA (Principal Component Analysis) and VAE (Variational
Autoencoder) are both unsupervised techniques used for dimensionality reduction,
but they take fundamentally different approaches. PCA is a deterministic, linear
method that compresses data by maximizing variance, whereas VAEs use deep neural
networks and probability to capture non-linear relationships and generate
entirely new data. The paper's VAE implementation uses JAX/Flax. The goal is the
same — a compact, well-behaved latent space where kNN distances are meaningful —
and PCA is a perfectly valid stand-in at this time.

**KSG estimator.** The DemInf paper uses non-parametric estimators based on
k-nearest-neighbors, specifically the KSG estimator. For each (state, action)
pair, find its k nearest neighbours in joint space. If a point's neighbours in
*state space* and *action space* match up well, MI is high. The digamma function
converts neighbour counts into an information score.

Imagine you have 50 people all making the same coffee recipe, plotted on a map
where the **X axis** is their starting hand position (state) and the **Y axis** is
their first hand movement (action). KSG asks, for each person: *"do my nearest
neighbors on X also tend to be my nearest neighbors on Y?"*

- Yes → your action is **predictable from your state** → high MI → good demo
- No → your action is **surprising given your state** → low MI → suspicious demo

It is essentially asking *"does this demo agree with the majority?"* With 50
episodes, the majority wins — episode 0 gets penalized not for being bad, but for
being alone.

**Score & filter.** Average the per-step scores across a full trajectory to get
one quality number per demo. Keep demos above threshold κ.

Two further choices follow the paper's own recommendations:

- **Relative actions** (`RELATIVE_ACTIONS = True`) — actions are converted to
  deltas from the current state, removing the positional confound so MI captures
  behavioural intent rather than where the arm happens to be.
- **Averaging over k** (`KNN_K_RANGE = (2, 7)`) — a single k can be noisy on small
  datasets, so scores are averaged over k=2..6. The paper found results are robust
  to the choice of k; this just reduces variance.
