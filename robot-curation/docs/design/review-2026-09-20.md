## 0. 结论先行

设计文档的分层、契约冻结顺序、对账思路是对的，可以继续用。问题集中在三类：

1. **对 v1 的几处关键描述与代码不符**（A 类，19 项）。其中 VLM 调用图、解码方式、数据集级模块的执行位置

## 1. 需要拍板的问题

### Q1 VLM 请求合并的一期范围 · 状态：待澄清

**事实**（v1 代码）：04 篇 §4.1 的前提是「同一条 episode 的同一批抽帧，本来要被 task_success、skill_profile 各问一遍」。
代码里不是这样：

| 调用 | 次数/条 | 图片 | 帧怎么来 | 条件 |
|-|-|-|-|-|
| task_success · probe | 8 次（每个采样时刻 1 次，顺序打乱） | 每次 2×机位数 张（参考帧 + 该时刻） | 0.5s 间隔解码，≤4 机位（`funnel.py:782-790`，`task_success.py:74-77`） | 每条必跑 |
| task_success · endstate | 每机位 2 次（完成?/失败?） | 每次 8 张，单机位 | 复用 probe 已解码的帧（`task_success.py:333-338`） | 每条必跑，不看 probe 结果 |
| task_success · 任务类型 / 判废护栏 / 取证仲裁 | 若干 | 仲裁用裁剪放大图 | 同上 | 分别在关键词未命中 / 判废且为原始标注 / 弃权时触发 |
| skill_profile · caption | 1 次 | ≤4 机位 × 8 帧 | **另一次全帧率解码**后 linspace 取 8 帧（`caption.py:95-106`） | 只对判决 = keep 且去重后的条目跑（`run.py:823-883`） |
| skill_profile · 归纳/审计 | 数据集级，纯文本 | 无 | — | — |
| 漏斗前 · 无标注补 caption | 1 次 | 同 caption | 同 caption | 只对没有任务标注的条目，漏斗前全量跑（`run.py:700-724`），结果被 skill_profile 复用 |

两个模块的帧集不同、执行时机不同、调用结构不同（一个是十几次请求的证据链，一个是单次请求），
不存在「同一批帧被问两遍」。现有两个模块之间几乎没有天然的合并对象。

**选项**：
- **A（推荐）**：一期交付合并**框架**（MergeUnit / MergeStrategy / MergeLimits / 按 key 拆回 / 单项降级单发 / usage 摊派），
  用契约测试加一个示例 VLM 模块验证；现有两个模块保持 v1 调用图不动，对账零风险。
  新 VLM 模块按「单次请求、声明帧策略」的规范接入，帧策略相同的自动合并 —— 这正是需求里「5 个模块合并」的场景。
- B：在 A 之上，把 caption 并进 task_success 的某次请求。需要统一抽帧，caption 的输入随之变化，
  技能画像与 v1 不再可比，要接受对账口径放宽；而每条只省 1 次请求（约 1/15）。
- C：连模块内部的多次调用也合并（probe 8→1 等）。这是改算法，违反「实现思路不能改」，不推荐。

**影响**：04 篇 §4、§3 计划示例、05 篇 §1、10 篇 §3.4、W6 范围。F2.4 验收①在 A 方案下由示例模块承担。

### Q2 解码与分档：去掉 decode stage 和帧缓存？ · 状态：待澄清

**事实**：v1 没有任何帧缓存，帧只在内存里，用完即释放（`funnel.py:466-468, 557`）。
- 视频-动作同步必须**全帧率**解码（lag 分辨率 = 帧间隔，`funnel.py:512-528` 注释），视觉质量从同一批帧里按 0.5s 抽稀，
  两者在同一个 UDF 里共享一次解码、逐机位串行。
- task_success 自己再解码一次（0.5s 间隔，448px，≤4 机位）；caption 第三次（全帧率）；证据帧导出第四次（首个机位）。

设计里的 `curation decode`（00 §4 ③、02 §3.3、04 §3 的 decode stage、09 的 200Gi 帧缓存）要把「三方复用的帧」落盘：
全帧率帧单条 episode 就是 GB 级（60s × 30fps × 3 机位，448px 原始约 1.8GB），640 条约 1TB；
用 JPEG 压缩又会让视觉质量、同步的读数偏离 v1，「逐位一致」直接不成立。

**选项**：
- **A（推荐）**：删掉 decode stage 和帧缓存。`check` 允许一次传**同一档内**的多个模块
  （`--modules visual_quality,video_action_sync`），同进程共享一次解码，结果仍按模块分文件落盘；
  单独重试其中一个模块时接受重复解码。档的划分照搬 v1：数值档 → 硬门① → 帧档 → 硬门② → task_success → 判决 → 去重 → 技能画像。
- B：保留 decode stage，但只缓存 VLM 用的抽稀帧（0.5s / 448px，体积可控，且须无损格式）；视觉/同步仍在进程内全帧率解码。
- C：维持原设计。

**影响**：00 §4、02 §3.3–3.4、04 §2–3、09 §2.1（cache 卷）/§5、11 篇 W3 验收。

### Q3 黄金对账数据集 · 状态：待澄清

**事实**：`umi_640_notask` 在 v1 代码/README/测试里没有任何出现，只存在于部署环境。按代码推断它跑不到这些路径：
- `kinematic_limits`：`umi` 不在运动学规格库（9 款里没有，`registry/profiles/`），**整项跳过** —— 对账表里这一行是空转；
- 原始标注路径：无标注 → 全部走「自产 caption」兜底，判废护栏（要求 `task_src == "原始标注"`）、标注分歧检出、
  「标注分歧」裁决线都不会触发；
- 取证仲裁的外部机位线：umi 两路都是腕部相机（`dataset_profiles/umi.yaml`）；
- `motion_quality` 的卡死/饱和子项：umi 的 action ≡ 下一帧 state，同源自弃权（`motion_quality.py:266`）。

**选项**：
- **A（推荐）**：增加第二基线 `droid_lerobot` 前 50 条（使用文档同款：franka 在规格库、3 机位含外部机位、
  50 条里 22 条无标注 + 28 条有标注），两个基线都要过。D15 与 F1.1/F4.2 追加一条，不改原有条款。
- B：只用 `umi_640_notask`，在 10 篇里写明覆盖缺口，缺口部分靠单元测试兜底。
- C：换别的数据集（请指定）。

### Q4 需求里的「自定义」提交方式，要不要留一个入口 · 状态：待澄清

需求原文：前端「先使用后端的 helper API 拿到并行优化后的参数后，再通过"自定义"的方式提交任务」。
D5 已定为「只有标准模式，helper 在 Daemon 内部必经」。我不重开 D5，但它留下两个实际问题：
①「合并粒度、并发度调优」是需求点名的后续独立任务，调优要反复提交不同计划，没有入口就只能改服务端配置；
②文档说 planner 的决策「可观测、可干预」，但没有任何接口能看到计划。

**选项**：
- **A（推荐）**：UI 和普通调用方仍只有标准模式；加只读的 `GET /api/v1/tasks/{id}/plan`；
  `POST /tasks` 接受可选的 `plan_overrides`（合并策略、各档并发、批大小），标注为调优/调试用，UI 不露出。
- B：严格按 D5，不留入口；调优时改站点配置。
- C：回到需求原文的两步式（`POST /plan` 拿参数 → 带参数提交）。

### Q5 任务的「改」与失败/停止后的续跑 · 状态：待澄清

需求要求任务「增删改查」，且「错误」任务可重试。文档现状：创建后只能改名；`stopped` / `failed` 是终态，
`POST /retry` 只定义了「重试失败模块」，对任务级 `failed`（没有模块结果）和 `stopped`（跑了一半）没有语义；
`start_now=false` 的任务停在 `queued`，和「排队等 worker」共用一个状态。

**选项**：
- **A（推荐）**：加「待启动」状态（`start_now=false` 进入，可改全部配置，启动后锁定）；
  `stopped` / `failed` 支持「继续运行」= 建 `resume` 子任务，只跑没完成的模块 × episode；另加「复制为新任务」。
- B：不加状态。创建后只能改名；`stopped` / `failed` 只能「复制为新任务」从头跑。
- C：只做「继续运行」和「复制为新任务」，不做待启动状态（`start_now` 参数删掉）。

### Q6 任务列表的分页形态 · 状态：待澄清

需求：「标准的分页逻辑和 Lazy Loading」，同时要求使用习惯对齐火山控制台。文档与静态稿选的是游标分页 +「加载更多」。
火山控制台的表格一律是页码 + 每页条数 + 总数。这会改 REST 契约（C4），要在冻结前定。

**选项**：
- **A（推荐）**：任务列表用页码分页（`page` / `page_size` / `total`，任务量级下 OFFSET 没有性能问题）；
  Lazy Loading 用在重内容上：episode 预览图、报告明细表、视频、日志；裁决队列和日志流保留游标。
- B：维持游标 +「加载更多」。
- C：API 保留游标并返回 `total`，UI 只给「上一页 / 下一页」。

### Q7 Agent 入口：links 由谁产出 · 状态：待澄清

02 篇 §6 让「任何 CLI 命令的 `--json` 输出」带 `links`，指向 `/tasks/<id>/report`。但原子 CLI 不经过 Daemon，
没有 task 概念，直接跑出来的结果在 Web 上没有对应页面。

**选项**：
- **A（推荐）**：Agent 主入口定为 REST API；CLI 增加一组薄客户端命令（`curation task create|get|wait|retry|adjudication`），
  内部调 Daemon 的 REST，返回带绝对 URL 的 `links`；原子命令（preflight/check/...）不产出 `links`。
- B：原子 CLI 直跑的结果也要能在 Web 打开 —— Daemon 提供「把已有 run 目录导入为任务」的接口。
- C：只有 REST 带 `links`，CLI 不加客户端命令。

### Q8 文档落点 · 状态：待澄清

飞书文档头写明「以仓库 Markdown 为准，本文档为汇总副本」。

**选项**：
- **A（推荐）**：改仓库 12 篇 Markdown 并 commit，再把改动同步到飞书副本的对应章节（保留文档链接和已有评论）。
- B：只改飞书文档。
- C：只改仓库，最后整体重新导出一份新的飞书文档。

## 5. 默认处理的产品细节（不同意请在逐项过时否掉）

| # | 事项 | 默认 |
|-|-|-|
| D-1 | 同时运行的任务数 | 默认 1（v1 也是「有任务在跑」时禁用按钮），其余排队；`maxRunningTasks` 可调，>1 时 Daemon 按任务数均分 VLM 并发预算（子进程架构下进程内信号量管不到跨进程） |
| D-2 | 429/5xx 自适应降并发放在哪层 | CLI 进程内的 VLM 客户端（Daemon 管不到运行中子进程的闸门），Daemon 只给初值并采集事件 |
| D-3 | 深链带多个数据集 | 新建页进入批量模式：共用一套配置，一次创建 N 个任务，交付目录各自为 `<根>/<数据集>-<MMDD>` |
| D-4 | CPU 档并发 | CLI 默认 1（需求原话）；Daemon planner 默认 `min(8, 核数/4)`，记为 D18 并注明与需求「可以默认用 1」的关系 |
| D-5 | 进度模型 | `progress` 改为分 stage 的数组（每档独立进度、耗时、预计剩余），对应 v1 任务卡 |
| D-6 | 创建任务的幂等 | `POST /tasks` 也支持 `Idempotency-Key`（Agent 重试最容易重复建任务） |
| D-7 | `/metrics` | 与探针一样豁免鉴权，但只监听集群内端口 |
| D-8 | 任务列表的实时性 | 列表页轮询（5s，仅当有非终态任务），不单独做全局 SSE |
| D-9 | 信号协议 | SIGTERM = 收尾当前 episode 后退出（暂停/优雅停机）；SIGINT = 取消在飞请求立即退出（停止）；超时 SIGKILL |
